当前执行基线、能力边界与验收门禁总览
客户：振兴集团 版本：v1.2 信息基线：2026年8月12日

01 项目概述与目标

1.1 项目背景

振兴集团（马来西亚）现有上千名内部员工，当前 IT 支持与 HR 服务依赖传统邮件问答方式，由 20-30 名专职人员处理。知识沉淀在 SharePoint 中，缺乏智能化检索和自助服务能力。

客户希望引入灵基平台作为员工获取服务和后台处理问题的唯一工作台，通过 AI 智能体实现自助问答、智能提单、知识飞轮的端到端闭环。

1.2 项目目标

1000+
目标覆盖员工数
3
业务线（Tech GBS / People GBS / BP）
75
工单分类项（二级）
1 平台
灵基作为唯一工作台

1.3 核心价值主张

一句话目标：能自助的自助，自助不了的转人工，且转人工时信息完整、不用重复填。
终态愿景：灵基取代邮件成为统一服务入口，AI 持续学习形成知识飞轮；该愿景不等于 8/31 试运行范围已全部具备。

2.2 核心痛点

🔍 信息获取效率低
员工遇到问题需发邮件等待人工回复，平均响应依赖人力排队。SharePoint 无语义搜索，查找文档靠关键词碰运气
📋 工单流程不透明
邮件问答无状态追踪，员工不知道问题处理到哪一步。缺乏 SLA 考核，响应时效无保障
🧠 知识无法沉淀

🔐 缺乏权限管控
知识按部门/子公司有隔离需求，但 SharePoint 权限体系无法与 AI 检索打通

03 解决方案蓝图

3.1 目标架构图（当前确认方案）

阅读说明：本图按当前确认方案展示部件关系。员工/处理人 Skill、工单服务、Work 内嵌页面与基础 DC 属当前交付主线；工单后台负责生成并保存分配、答复、状态变化和 SLA 等消息事件，“我的工单/我的任务”内嵌页面读取并展示最新数据、未读状态和提醒。灵基原生菜单、角标和消息中心不在可改范围内。

3.2 端到端目标时序图

说明：本图按当前确认方案展示完整流程。灵基原生菜单、角标和消息中心不可修改，因此不依赖后台向灵基原生能力推送；工单后台建立独立消息机制，“我的任务/我的工单”作为嵌入 Work 的后台页面，在打开时增量加载消息，并可通过轮询或长连接刷新任务、未读状态和提醒。邮件、企业微信等外部通知仍由工单后台按需发送。

3.3 知识生命周期图

3.4 用户旅程

旅程边界：灵基原生菜单、角标和消息中心不可修改。消息能力由工单后台实现：业务事件写入消息表或事件队列，并按用户维护未读状态；嵌入 Work 的“我的任务/我的工单”页面负责加载和刷新消息、任务及工单变化。页面未打开时不承诺灵基原生提醒，必要时由工单后台通过邮件、企业微信等外部渠道补充通知。

阶段一：员工自助问答

员工进入灵基 Work → 向智能体提问 → 智能体检索 DC → 返回答案及引用来源 → 员工判断是否解决
  • 已解决：旅程结束，不创建工单。
  • 未解决：进入智能提单阶段。

阶段二：员工确认提单

智能体根据对话生成工单草稿 → 员工检查、编辑并确认 → 智能体调用 MCP 创建工单 → 工单后台返回工单号 → Work 展示提交成功回执

关键规则：AI 只生成草稿，员工明确确认后才创建工单，不允许“自动建单”。

阶段三：后台分配工单

工单后台接收工单 → 按分类、处理组和规则自动分配 → 工单进入“处理中” → 工单进入对应处理人的“我的任务”

消息机制：工单分配成功后，后台同步写入面向处理人的消息事件和未读状态；嵌入 Work 的“我的任务”页面在打开或刷新时获取该事件，并将新任务置顶或高亮。若页面保持打开，可通过轮询或长连接及时刷新；不修改或依赖灵基原生通知能力。

阶段四：处理人主动查看并处理

处理人进入灵基 Work → 打开“我的任务” → 查询新分配及待处理工单 → 查看详情并编写答复 → 提交答复，后台记录处理结果

状态规则：处理人答复后，工单仍保持“处理中”，等待员工确认是否解决。

阶段五：员工查询答复并确认

员工进入灵基 Work → 打开“我的工单” → 查看最新状态和人工答复 → 判断问题是否解决
  • 未解决：员工补充说明，工单保持“处理中”，处理人后续通过“我的任务”继续处理。
  • 已解决：员工确认关闭工单并提交评价，工单后台记录评分及 KPI。

消息机制：处理人答复、状态变化和关闭邀评等事件由工单后台写入面向提交人的消息记录；嵌入 Work 的“我的工单”页面展示未读数量、新答复标识和状态变化，用户查看后更新已读状态。

条件分支：知识沉淀

筛选符合知识沉淀条件的已处理工单 → 处理人整理知识产物 → 处理人确认后上传 DC → 完成权限、解析与索引 → 供后续智能问答检索使用

能力状态：知识产物一键上传计划于 2026-08-21 发布，发布后需完成权限、回执、解析、索引和检索验收；该分支不是每张工单的必经步骤。

3.5 知识流转说明

当前方案：1、初始化：手动上传政策类文档（20-25 份 PDF）到 DC，完成知识初始化
持续沉淀（Foundation 最新边界）：对话过程只支持加工后的知识产物写入 DC，对话附件不能直接入库；未加工原文件如需作为知识源，走智能体详情/DC 管理界面点击上传，以减少不必要的对话点数消耗。HelpDesk 工单附件默认仅生成脱敏摘要并并入知识产物

4.4 状态变化在"我的工单/我的任务"中的体现

工单后台在业务事务完成后生成面向具体用户的消息事件并维护未读状态；Work 菜单挂载的“我的工单/我的任务”是工单后台提供的内嵌页面，负责加载、刷新和展示这些消息。这里的“消息”属于工单后台页面能力，不修改灵基原生菜单、角标或消息中心：

业务事件用户看到的位置展示形式
新工单分配处理人→我的任务新工单出现在待办列表顶部（含标题/分类/提问人/SLA 时限）
处理人答复员工→我的工单→工单详情答复记录更新，工单保持“处理中”，等待员工确认
工单状态变更员工→我的工单工单列表状态列实时更新
SLA 即将超时处理人→我的任务SLA 标红/排序前置
员工确认解决员工→我的工单→工单详情展示评价入口，员工确认并提交评价
员工完成确认与评价员工→我的工单状态更新为“已关闭”，后台记录评分及 KPI
工单转派新处理人→我的任务新工单出现在待办列表，并显示未读/新任务标识

内嵌页面消息机制

能力实现要求边界
事件生成工单分配、转派、答复、用户补充、状态变化、关闭邀评和 SLA 预警成功后，由工单后台写入消息事件；业务数据与事件写入需保证一致性不调用灵基原生消息中心
用户路由按提交人、当前处理人和授权范围生成接收对象，记录 eventId、ticketId、事件类型、摘要、发生时间和未读状态不得向无工单权限用户生成或返回消息
页面加载“我的任务/我的工单”内嵌页面按当前用户增量读取消息和工单数据，支持未读数、新任务/新答复高亮、按时间排序及已读标记未读数只显示在内嵌页面内，不能要求修改 Work 原生菜单角标
页面刷新页面首次打开必须拉取未读事件；保持打开时优先使用轮询，若部署环境支持可升级为 SSE/WebSocket 长连接页面关闭时只保证后台可靠存储，不能承诺灵基原生弹窗或实时提醒
失败与补偿事件写入失败需重试并可审计；页面使用游标或时间戳增量同步，重复读取按 eventId 去重消息展示失败不得影响工单业务事务结果

5.2 SLA 规则

Agent 侧 SLA

  • 按工单分类设定不同的响应时间和解决时间
  • 超时触发告警并升级
  • 具体标准遵循客户提供的 Category Catalog 文档

提单人侧 SLA（当前客户基线）

  • 第一期不自动关单；工单最终关闭必须由提交人明确确认。
  • 等待用户补充资料期间第一期暂不暂停 SLA，但 SLA 超时本身不触发自动关闭。
  • 处理人认为问题已解决时执行“提交已解决”，工单进入“待提交人确认”；提交人可确认关闭或填写原因驳回。
  • 长期无回复自动关单属于后续待确认方案，只有客户明确修改 Q-06 口径并确认规则、提醒和审计要求后才能启用。

5.3 审批流程（IT Service Request）

涉及新设备申请、新软件安装、权限变更、VPN 开通等场景需走审批流程：

提交申请 → Level 1 审批 → Level 2 审批（如需） → 分配处理

具体审批人和工作组待客户确认后配置。
