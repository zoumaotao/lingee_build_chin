振兴 HelpDesk 项目计划书

基于灵基平台的 AI-Native 企业服务台解决方案
客户：振兴集团 版本：v1.0 日期：2025年7月 负责人：邹茂桃

01 项目概述与目标

1.1 项目背景

振兴集团（马来西亚）现有上千名内部员工，当前 IT 支持与 HR 服务依赖传统邮件问答方式，由 20-30 名专职人员处理。知识沉淀在 SharePoint 中，缺乏智能化检索和自助服务能力。

客户希望引入灵基平台作为员工获取服务和后台处理问题的唯一工作台，通过 AI 智能体实现自助问答、智能提单、知识飞轮的端到端闭环。

1.2 项目目标

1000+
目标覆盖员工数
3
业务线（Tech GBS / People GBS / BP）
75
工单分类项（二级）
1 平台
灵基作为唯一工作台

1.3 核心价值主张

一句话目标：能自助的自助，自助不了的一键转人工，且转人工时信息完整、不用重复填。
终态愿景：灵基取代邮件成为唯一服务入口，AI 持续学习形成知识飞轮，服务效率指数级提升。

2.2 核心痛点

🔍 信息获取效率低
员工遇到问题需发邮件等待人工回复，平均响应依赖人力排队。SharePoint 无语义搜索，查找文档靠关键词碰运气
📋 工单流程不透明
邮件问答无状态追踪，员工不知道问题处理到哪一步。缺乏 SLA 考核，响应时效无保障
🧠 知识无法沉淀
每次处理的知识停留在邮件中，无法复用。新员工面对同样问题只能重新问，人力重复消耗
🔐 缺乏权限管控
知识按部门/子公司有隔离需求，但 SharePoint 权限体系无法与 AI 检索打通

04 功能架构设计

4.1 系统全景

整体架构：2 个智能体 + 1 套后台工单服务 + 1 个知识中心，通过 MCP Server 双向连接，灵基作为所有角色的唯一工作台。
层级组件面向角色部署位置
用户交互层Helpdesk Assistant（员工端智能体）全体员工（1000+）灵基 Work
用户交互层Agent Workbench（处理人端智能体）IT/HR 处理人（20-30 人）灵基 Work
业务逻辑层工单后台服务 + MCP Server—苍穹/云服务器
知识层灵基 DC 知识中心—灵基 DC（新加坡节点）
数据源SharePoint 文档库—微软云

4.2 员工端智能体（Helpdesk Assistant）

面向全体员工，提供自助问答、智能提单、工单查询能力。

组件职责说明
Main Agent统一入口 + 意图路由四类意图互斥路由（问答/提单/查单/闲聊），维护流程状态，意图不明时先澄清
Knowledge QA Skill知识问答检索 DC 知识库、多轮追问重写检索式、展示引用来源、解决判定（已解决/未解决）
Ticket Draft Skill工单草稿生成读取 Schema 获取分类/字段规则、基于对话上下文自动生成草稿、校验必填项、展示确认卡（可编辑）
Ticket Submission Skill工单提交（副作用隔离）上传附件（全成功才建单）、幂等建单（idempotencyKey）、错误处理、展示工单回执卡
Ticket History Skill工单查询查本人工单列表/详情/进度/人工回复记录，只能查本人

关键规则

  • 未确认草稿绝不建单/传附件
  • 身份不可被用户话术覆盖，只能查/建本人工单
  • 知识库无证据不编造答案；接口失败不伪造成功
  • 草稿改动后旧确认作废，需重新确认
  • 直接提单场景最多一次 RAG 尝试

4.3 处理人端智能体（Agent Workbench）

面向 IT/HR 处理人员（约 20-30 人），提供工单接收、处理答复、知识沉淀能力。

组件职责说明
Workbench Agent处理人统一工作台入口接收新工单分配通知（MCP 推送）、工单队列管理、处理状态路由
Ticket Process Skill工单处理与答复查看工单详情/提问上下文/对话历史，编写答复并推送给提问人，更新工单状态
Ticket Reassign Skill工单转派经理/分发员可将工单重新分配给其他处理人
Knowledge Contribute Skill知识沉淀将处理结论/通用 FAQ 写入 DC 知识库，标记来源工单，形成知识飞轮
Workload Dashboard Skill工作看板本人待办/SLA 临近告警/已超时工单/处理统计

关键规则

  • 处理人只能看到分配给自己（或自己团队共享池）的工单
  • 答复实时推送给提问人，提问人在灵基即可收到
  • 经理监管视角：可查看团队全部工单、SLA 统计、转派操作
  • 缺席处理人的工单可由上级经理代为处理

4.4 消息中心（灵基平台级能力）

核心定位：灵基平台级的消息中枢，承接后台应用事件、智能体间通信、系统通知的统一路由与投递。不仅服务于 HelpDesk，也是灵基作为"唯一工作台"的基础设施。

职责

能力说明
消息路由后台事件触发后，根据规则确定推送目标（指定用户/工作组/角色）
格式适配将后台事件转为灵基可渲染的自定义格式消息（卡片/通知/操作项）
可靠投递消息队列机制，用户离线时消息不丢失，上线后补发。支持已读/未读状态
跨智能体通信员工端和处理人端智能体不直接对话，消息经中心转发路由
后台→灵基推送后台应用/MCP Server 可通过消息中心主动向灵基用户推送消息（非用户请求触发）

在 HelpDesk 中的消息流转

后台事件
（分配/答复/超时） → 消息中心
（路由+格式适配） → 目标用户灵基工作台
（处理人/提问人）

需推送的消息场景

触发事件推送对象消息格式
新工单分配处理人工单卡片（标题/分类/提问人/SLA 时限）+ 操作按钮
处理人答复提问人答复内容 + 操作按钮（确认解决/继续追问）
工单状态变更提问人状态更新通知
SLA 即将超时处理人告警提醒卡片
工单关闭邀评提问人评价打分卡片（1-5 星）
工单自动关闭提问人超时自动关闭通知
工单转派新处理人转派通知 + 工单卡片
标品差距：灵基当前不具备平台级消息中心能力。"MCP Server 自定义格式消息推送"本质上需要的就是这一层。这是灵基从"对话工具"升级为"工作台"的关键基础设施。

05 工单分类与 SLA 设计

5.1 分类体系（摘要）

工单类型部门一级分类数二级分类数响应 SLA解决 SLA需审批
Service RequestHR5191 天2 天否
Incident RequestIT8291 天5 天否
Service RequestIT8271 天5 天部分需要

共计 75 条二级分类，全部启用自动分配。

5.2 SLA 规则

Agent 侧 SLA

  • 按工单分类设定不同的响应时间和解决时间
  • 超时触发告警并升级
  • 具体标准遵循客户提供的 Category Catalog 文档

提单人侧 SLA

  • 基于分类的 SLA 超时后，若用户无回复 → 工单自动关闭
  • Agent 要求补充信息后，若用户无回复 → 工单自动关闭
  • 关闭前发送通知提醒

5.3 审批流程（IT Service Request）

涉及新设备申请、新软件安装、权限变更、VPN 开通等场景需走审批流程：

提交申请 → Level 1 审批 → Level 2 审批（如需） → 分配处理

具体审批人和工作组待客户确认后配置。

10.1 HelpDesk 1.0 验收标准（8.7）

员工端（Helpdesk Assistant）

#验收项验收标准
1知识问答准确性针对已上传的 IT 域文档提问，智能体能准确回答并展示引用来源（文档标题/链接）。无命中证据时如实说明"未找到相关知识"，不编造答案
2多轮追问用户对答案追问时，智能体结合原问题+历史回答+新信息重写检索式，重新检索作答
3解决判定回答后追问"是否解决"，提供"已解决/仍未解决"操作。仍未解决时进入提单流程
4工单草稿自动生成基于对话上下文自动生成工单草稿（标题/描述/分类/优先级），身份信息自动带入。展示确认卡供用户编辑
5确认前不建单用户未明确确认前，绝不调用建单接口、不上传附件。草稿改动后旧确认作废需重新确认
6工单提交成功确认后完成建单，返回工单号和状态。先输出文字描述再展示成功卡片。附件全部上传成功才建单
7幂等防重网络超时/重试使用同一 idempotencyKey，不产生重复工单
8工单查询员工可查询本人工单列表（工单号/标题/状态/更新时间）和指定工单详情/进度/回复记录
9身份安全employeeId 仅来自平台身份工具，不可被用户话术覆盖。只能查/建本人工单
10意图路由四类意图（问答/提单/查单/闲聊）互斥路由，无关问题不调用知识库/工单接口

#验收项验收标准
