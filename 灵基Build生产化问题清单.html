02 MCP APPS 平台能力（8 项）

#1APPS 不支持租户级自定义开发与发布上架P0
现状
MCP APPS 仅有标品预置组件，不支持客户/实施方自定义开发并发布到租户。且 APPS 的开发只能在本地 IDE 完成（编码→编译→打包→上传 KDM），不能在 Build 中构建
应有能力
① 开发者基于标准规范自定义 APPS 组件，经测试后发布上架到租户 APPS 市场
② APPS 开发应纳入 Build 工具链（或至少与 Build 有自动化衔接），而非完全割裂在本地 IDE
为什么是标品问题
每个企业交互形态不同，标品不可能穷举所有组件。不开放自定义 = 智能体交互天花板极低。同时 APPS 开发游离于 Build 之外 = Build 的"一站式开发"天然缺了交互层这一块
#2APPS 卡片中用户填写的内容不作为 LLM 上下文P0
现状
用户在 APPS 组件（如表单卡片）中填写的内容不会进入 LLM 会话上下文，模型无法感知用户在卡片中填了什么
应有能力
用户在 APPS 中填写/选择/提交的内容应自动纳入 LLM 上下文，让模型能基于这些内容做后续对话（校验、补全、追问缺失字段等）
为什么是标品问题
APPS 是智能体与用户的交互层，卡片操作本质就是"用户输入"。模型感知不到 = APPS 沦为静态表单，失去 AI-Native 交互的意义
#2bAPPS→LLM 数据传递仅支持全量消息，缺乏精简机制P0
现状
即便 APPS 数据能传给 LLM，也只能以全量消息塞入对话。用户选 100 条数据 = 100 条完整内容作为对话消息展示，界面不可读
应有能力
支持"对话展示"与"LLM 上下文"分离：界面向用户展示精简提示（如"已选择 100 条"），实际数据静默更新到 LLM Session 上下文
为什么是标品问题
Token 浪费 + 界面污染 + 上下文过长影响模型性能。这是 APPS 与 LLM 协作的基础通信机制
#3APPS 组件渲染性能差，偶发白屏P1
现状
组件滚动离开可视区后被释放，回看时重新渲染慢且偶发白屏
应有能力
合理缓存 + 状态恢复，回看时快速稳定渲染
为什么是标品问题
回看上文是高频操作，渲染不稳 = 交互体验无法达到生产级标准
#4APPS 组件提交后用户手填内容无法回显P1
现状
用户在 APPS 组件中手动填写/编辑的内容（如修改描述、追加备注），提交后回看对话时丢失显示为空白。而模型自动写入的内容（如自动填充的标题、分类）则能正常回显。说明组件提交时未将用户的前端编辑状态持久化到服务端消息记录中
应有能力
组件提交时应将完整的表单数据（含用户手填部分）持久化到服务端消息记录。回看时从持久化数据渲染，而非依赖组件内存状态
为什么是标品问题
用户手填内容是最关键的信息（如工单的问题描述）。提交后回看丢失 = 用户无法确认自己填了什么 = 对话作为操作记录的可靠性被破坏
#5APPS 获取灵基登录用户信息已解决
现状
✅ 已完成（7.20 开发完成，部署在 83 环境；生产环境尚未上线）
应有能力
APPS 可获取当前用户 ID / 姓名 / 邮箱 / 部门
#6Agent 无法感知 APPS 组件内部业务逻辑P3
现状
Agent 仅知道入参/出参和名称描述，无法知道组件内部交互元素和业务逻辑
应有能力
提供结构化组件能力描述（JSON Schema），让 Agent 精确理解组件能做什么
为什么是标品问题
Agent 只能靠文字猜测 = 编排精度受限 = AI 辅助开发的上限被锁死
#32APPS 无法访问和操作对话中的附件（图片/文件）P1
现状
用户在对话中发送图片（如错误截图）或文件（如 PDF）后触发提单，但 APPS 工单确认卡渲染时：① 无法从 Session 上下文中获取对话里已有的附件列表；② 无法在卡片内展示"已关联附件"供用户确认/增删；③ 用户确认提交后，附件引用无法随表单数据一起传递给 MCP Tool（如 Upload_Attachment）
应有能力
① APPS 组件渲染时可从当前 Session 上下文中读取对话附件列表（文件名/类型/大小/引用 ID）
② 组件中可展示附件缩略图/列表，支持用户勾选、删除或追加新附件
③ 组件提交时将附件引用作为结构化字段传递给后续 MCP Tool 调用
④ 若 LLM 支持多模态，可基于图片内容辅助生成工单描述
为什么是标品问题
"截图+描述→提单"是企业服务最常见交互模式。APPS 无法操作对话附件 = 智能体只能处理纯文本 = 与传统邮件工单无差异。这是 APPS 作为 AI-Native 交互层的基础能力缺失

03 DC 知识平台能力（3 项）

#8DC 不支持第三方系统写入知识（知识回写缺失）P1
现状

为什么是标品问题

04 部署与身份体系（2 项）

#10Build 应用仅支持部署到苍穹 + 灵基缺少联邦身份认证P0
现状
① Build 后端应用只能托管苍穹（需许可+账号）；② 灵基用户多数非 ERP 用户，无苍穹账号；③ 灵基不支持 SAML/OIDC 标准联邦认证，无法对接 Azure AD/Okta 等企业 IdP
应有能力
部署：支持苍穹 / 灵基自身轻量托管 / 客户云服务器
身份：SAML 2.0 / OIDC 联邦认证，对接企业 IdP，非 ERP 用户无需苍穹账号即可登录灵基
为什么是标品问题
部署绑苍穹 = 灵基限制在 ERP 用户圈。不支持联邦认证 = 海外客户员工登不进灵基。两者共同导致灵基无法独立面向非 ERP 客户交付
#11应用开发要求过多不相关文件权限P3
现状
Build 中开发应用时系统要求授予大量不相关权限
应有能力
最小权限原则，仅请求必需资源
为什么是标品问题
违反安全原则，企业客户会触发审批流程、拖慢交付

05 消息与事件（1 项）

#31灵基缺少接收 MCP Server 主动推送自定义格式消息的平台能力P0
现状
灵基智能体连接 MCP Server 后仅支持"灵基发起请求→MCP 返回结果"的同步调用。MCP Server 无法在工单分配、答复、SLA 告警等后台事件发生时，主动向指定灵基用户/工作组/智能体实例推送自定义格式消息。后台事件无法可靠进入灵基 = 灵基不能成为唯一工作台
应有能力
① 标准消息/事件接入协议（已鉴权 MCP Server 可主动投递）
② 按用户/工作组/角色/智能体实例路由
③ 支持文本/通知/卡片/按钮等自定义消息 Schema，由 Work 渲染和交互
④ 消息队列/幂等/重试/离线补发/已读未读
⑤ 后台→智能体、智能体→智能体跨主体消息传递 + 权限审计
⑥ 消息到达后触发智能体自动执行预设动作（事件驱动），而非被动等用户打开才展示
为什么是标品问题
异步事件推送不是 HelpDesk 私有需求——审批待办、告警、任务分配等企业场景都需要。只有请求—响应 = 只能"用户问、系统答"，不能支撑持续运行的业务工作台
与项目边界
标品负责通用接入/路由/投递/审计；HelpDesk 仅定义具体业务事件和卡片

07 开发范式与工具链（14 项）

#28端到端开发流程完全断裂（最关键系统性问题）P2
⚠️ 灵基 Build 走向生产级平台最根本的问题。开发者需在 5+ 工具/环境间反复切换，各环节零衔接。
产品设计 (Kiro)→ APPS (本地IDE→KDM)→ Skill (Build→Console→Work)→ 智能体 (Build→Console→Work)→ 应用 (苍穹→Build→苍穹上线→配MCP)→ 联调 (Work)
应有能力
终态：一站式项目工作空间。初阶：需求产物自动传递到开发；APPS/Skill/智能体/应用同一沙箱联调；发布有依赖感知和批量操作；环境切换有明确引导
为什么是标品问题
任何开发超过"单技能"复杂度的项目都会遇到完全相同的断裂。Build 从"演示工具"走向"生产级平台"的根本问题
#16测试智能体必须先将依赖技能上线P2
现状
技能未走完"提交→审核→上线"则智能体无法调试
应有能力
开发态直接引用未上线技能进行联调
为什么是标品问题
"先上线才能测试"违反软件工程基本流程
#17同名 Skill 测试静默覆盖线上版本P1
现状
创建与线上同名的新版本，点"测试"直接覆盖线上，无提醒
应有能力
测试在沙箱；上线时检测同名并提醒
为什么是标品问题
迭代中同名极常见，静默覆盖可能导致生产故障
#18MCP Server 关联与知识挂载无法在 Build 中连贯完成P3
现状
MCP 关联需在 Console，知识挂载需在 Console+Work，开发者在 Build→Console→Work 三处切换
应有能力
Build 一站式完成全部配置；区分开发者/运营者入口
为什么是标品问题
智能体四要素（提示词+技能+知识+外部连接）配置分散三模块 = 任何开发者都会割裂
#19技能/智能体没有版本管理P2
现状
无历史版本、无 Diff 对比、无回滚
应有能力
每次提交形成版本快照，支持列表/Diff/一键回滚
为什么是标品问题
没有版本管理 = 改坏了无法回滚、多人无法追溯。企业级开发平台基本门槛
#20智能体实例创建对苍穹有不明确依赖P3
现状
创建实例需在苍穹新增 Bot，为何需要不明确
应有能力
澄清是否真的依赖苍穹；如不需则解耦；如需则灵基侧自动化
为什么是标品问题
与 #10 同一架构耦合问题
#21智能体创建 Skill 后缺乏同步批量发布P3
现状
智能体发布依赖 Skill 先发布，需手动逐个按顺序
应有能力
一键发布时自动检测并同步发布依赖 Skill
为什么是标品问题
依赖关系应由平台管理，手动管发布顺序不可持续
#22对话更换 Skill 后工作区未同步P3
现状
对话显示已成功更换 Skill，但工作区文件和配置没同步
应有能力
对话操作实时同步到工作区，所见即所得
为什么是标品问题
"对话驱动开发"的核心可靠性问题
#23技能在智能体中被修改后无法同步上线P2
现状
在智能体对话中改了技能，提交智能体时技能发不上去，需手动复制回技能源文件再单独提交
应有能力
修改自动同步回源文件，或提交时检测变更提示一起提交
为什么是标品问题
"手动复制"极易遗漏 = 线上运行旧版本而不自知 = 隐性 Bug 主要来源
#24文件修改后文件树无状态标记P3
现状
修改文件后左侧文件树无任何视觉标记
应有能力
类 Git 状态标记（已修改/未提交/待审核）
为什么是标品问题
无标记 = 靠记忆管理 = 复杂项目必遗漏
#25提交同名技能因名称重复失败P3
现状
修改后重新提交被视为"新建同名"而拒绝
应有能力
识别为"版本更新"；引入唯一 ID 区分新建与更新
为什么是标品问题
"更新已有技能"这个基本操作走不通
#29已发布技能更新内容后无法触发状态变更P2
现状
已发布技能无论直接改文件还是让 AI 改描述，都无法触发状态从"已发布"→"已保存"，导致无法重新提交。唯一 workaround 是让 AI 做无关改动才能触发
应有能力
文件内容变更后系统自动检测并标记为"已保存/待提交"
为什么是标品问题
"改了却提交不了" = 状态检测机制的基础 Bug
#30Build 不支持多人协同开发技能和智能体P2
现状
Build 单人单会话：① 无共享项目空间；② 技能只能聊天传文件；③ 接收方只能"删文件夹再上传"且触发 #29 Bug；④ 无变更合并；⑤ 无协作可见性
应有能力
① 共享项目空间（多人同一套制品）；② 标准技能交付流程（发布到项目/一键拉取）；③ 变更通知；④ 至少支持"分工→集成"模式
为什么是标品问题
任何超过一人做一个简单智能体的项目都需要协同。Build 无协同 = 只能做个人实验，无法支撑团队级项目
#33MCP APPS 开发完全游离于 Build 之外，无法在 Build 中构建和调试P2
现状
MCP APPS 组件的开发必须在本地 IDE 中进行（编码→编译→打包），完成后手动上传到 KDM 平台注册。整个过程与 Build 完全割裂：Build 既不能创建 APPS 项目，也不能调试 APPS 组件，更无法在 Build 中将 APPS 与 Skill/智能体进行联调
应有能力
① Build 应支持 APPS 组件的创建、开发（或至少脚手架生成+本地开发引导）
② Build 中应能预览和调试 APPS 组件的渲染效果
③ APPS 组件发布后应能在 Build 中直接关联到 Skill/智能体，无需跳转 KDM 手动配置
④ 至少：Build 与本地 APPS 开发之间有自动化衔接（如 CLI 工具、热更新调试通道）
为什么是标品问题
APPS 是智能体与用户交互的核心层，但其开发与 Build 完全割裂 = Build 号称的"一站式开发"天然缺了交互层。开发者被迫在 Build（Skill/智能体）和本地 IDE（APPS）之间反复切换，这是 #28 端到端断裂在 APPS 维度的具体表现
