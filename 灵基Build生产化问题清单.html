02 Console（1 项）

#1bConsole 组件上传未对租户开放P0
现状
自定义 APPS 组件的上传/注册通过 KDManage"业务组件"功能完成，但该入口是金蝶管理员可操作，租户无法自助上传自己开发的组件包
应有能力
① 在console对租户开放"业务组件"上传，客户可自助提交组件包
② 支持组件版本管理（上传新版/回滚旧版）
③ 支持审核机制（上传后审核通过才对智能体可用）
④ 支持启用/停用/下架管理
为什么是标品问题
上传能力已存在但未对外开放 = 客户每次组件变更都要走内部流程 = 不可持续。开放后才能形成"开发→上传→使用"的自助闭环。关联：#1（规范开放）、#33（Build 中开发）
方案推进
已纳入 MCP APPS 整体方案，Console 侧 API 需求已列出 → Build构建MCPAPPS方案设计（第九章 7.2 Console 侧）

03 MCP APPS 平台能力（8 项）

#1APPS 自定义开发能力未对租户开放（规范已有但未公开）P0
现状
APPS 自定义开发规范（dev-guide）、工程模板（demo.zip）、上传机制（KDManage 业务组件）均已存在且内部在使用，但未对租户/客户开放
应有能力
① 公开开发规范文档和工程模板；② 提供版本化 SDK 和 API 参考；③ 明确组件能力边界、安全约束和审核机制
为什么是标品问题
能力已有但未开放 = 客户只能依赖金蝶实施方代做 = 不可规模化。关联：#1b（Console 上传入口）、#33（Build 中开发）
方案推进
已有完整方案设计，涵盖规范公开、SDK 版本化、模板库等 → Build构建MCPAPPS方案设计（第九章 7.3 APPS 平台侧）
#2APPS 卡片中用户填写的内容不作为 LLM 上下文P0
现状
用户在 APPS 组件（如表单卡片）中填写的内容不会进入 LLM 会话上下文，模型无法感知用户在卡片中填了什么
应有能力
用户在 APPS 中填写/选择/提交的内容应自动纳入 LLM 上下文，让模型能基于这些内容做后续对话（校验、补全、追问缺失字段等）
为什么是标品问题
APPS 是智能体与用户的交互层，卡片操作本质就是"用户输入"。模型感知不到 = APPS 沦为静态表单，失去 AI-Native 交互的意义
#2bAPPS→LLM 数据传递仅支持全量消息，缺乏精简机制P0
现状
即便 APPS 数据能传给 LLM，也只能以全量消息塞入对话。用户选 100 条数据 = 100 条完整内容作为对话消息展示，界面不可读
应有能力
支持"对话展示"与"LLM 上下文"分离：界面向用户展示精简提示（如"已选择 100 条"），实际数据静默更新到 LLM Session 上下文
为什么是标品问题
Token 浪费 + 界面污染 + 上下文过长影响模型性能。这是 APPS 与 LLM 协作的基础通信机制
#3APPS 组件渲染性能差，偶发白屏P1
现状
组件滚动离开可视区后被释放，回看时重新渲染慢且偶发白屏
应有能力
合理缓存 + 状态恢复，回看时快速稳定渲染
为什么是标品问题
回看上文是高频操作，渲染不稳 = 交互体验无法达到生产级标准
#4APPS 组件提交后用户手填内容无法回显P1
现状
用户在 APPS 组件中手动填写/编辑的内容（如修改描述、追加备注），提交后回看对话时丢失显示为空白。而模型自动写入的内容（如自动填充的标题、分类）则能正常回显。说明组件提交时未将用户的前端编辑状态持久化到服务端消息记录中
应有能力
组件提交时应将完整的表单数据（含用户手填部分）持久化到服务端消息记录。回看时从持久化数据渲染，而非依赖组件内存状态
为什么是标品问题
用户手填内容是最关键的信息（如工单的问题描述）。提交后回看丢失 = 用户无法确认自己填了什么 = 对话作为操作记录的可靠性被破坏
#5APPS 获取灵基登录用户信息已解决
现状
✅ 已完成（7.20 开发完成，部署在 83 环境；生产环境尚未上线）
应有能力
APPS 可获取当前用户 ID / 姓名 / 邮箱 / 部门
#6Agent 无法感知 APPS 组件内部业务逻辑P3
现状
Agent 仅知道入参/出参和名称描述，无法知道组件内部交互元素和业务逻辑
应有能力
提供结构化组件能力描述（JSON Schema），让 Agent 精确理解组件能做什么
为什么是标品问题
Agent 只能靠文字猜测 = 编排精度受限 = AI 辅助开发的上限被锁死
#32APPS 无法访问和操作对话中的附件（图片/文件）P1
现状
用户在对话中发送图片（如错误截图）或文件（如 PDF）后触发提单，APPS 工单确认卡渲染时：① 无法从上下文获取对话里已有附件；② 无法在卡片内展示附件供确认/增删；③ 提交后附件引用无法随表单传递给 MCP Tool
应有能力
① 组件渲染时从 Session 上下文读取附件列表
② 组件中展示/管理附件，支持追加
③ 提交时附件引用作为结构化字段传递
④ 若 LLM 支持多模态，可从图片提取信息辅助生成工单
为什么是标品问题
"截图+描述→提单"是企业服务最常见模式。APPS 无法操作附件 = 只能处理纯文本 = 与传统邮件工单无差异
振兴实际场景
PRD 要求：确认卡需展示全部字段和附件供确认；可追加（PDF/JPG）；附件全成功才建单。实际：员工发蓝屏截图+文字，提单后确认卡应自动带出截图，用户可确认/删除/追加后提交

03 DC 知识平台能力（5 项）

#7DC 海外部署已解决
现状
✅ 已完成海外部署（新加坡节点）
#8DC 缺少外部系统推送写入知识的能力P1
现状
DC 不支持外部系统（如工单后台/MCP Server）通过 API 向指定智能体知识库推送知识。缺乏关联标识和版本管理
应有能力
标准写入 API，支持鉴权后的外部系统推送结构化知识到指定智能体知识库。需支持关联标识、增量更新、去重、版本管理
（实现上可与 #8b 合并为统一写入 API，通过调用方身份区分来源）
为什么是标品问题
工单处理结论、业务规则变更等需从后台实时写入。没有写入 API = 知识只能人工上传 = 无法形成飞轮
#8bDC 缺少灵基智能体运行时自动沉淀知识的能力P1
现状
灵基智能体在运行中（如对话识别到高频问题、处理人总结 FAQ），无法将生成的知识自动写入所属智能体知识库。智能体只能消费知识，不能生产知识
应有能力
智能体运行时可通过内部接口将知识写入 DC，支持标记来源（对话/工单）、质量审核机制（自动写入 vs 人工审核后写入）
（实现上可与 #8 合并为统一写入 API，智能体作为内部调用方走相同接口）
为什么是标品问题
智能体"越用越聪明"的核心 = 运行中自动沉淀。不能自动沉淀 = 无法自主进化 = 知识飞轮闭环的最后一环缺失
#8cDC 缺少主动拉取外部数据源的连接器框架P2
现状
DC 无法主动从外部数据源（如 SharePoint、Confluence、Google Drive）拉取文档并增量同步。唯一方式是人工下载后手动上传
应有能力
通用连接器框架：① 对接主流文档平台（SharePoint/Confluence 等）；② OAuth 等标准认证；③ 增量变更检测（仅同步新增/修改）；④ 定时调度或 Webhook 触发；⑤ 同步后自动进入 DC 加工流程
为什么是标品问题
企业知识大量存在 SharePoint 等平台且持续更新。DC 不能主动拉取 = 知识只能一次性搬运 = 时效性无法保障。振兴 2TB SharePoint 是 Phase 3 核心需求，但连接器是通用平台能力
#9DC 缺少完整的知识权限体系（检索存在越权仅是表面现象）P1
现状
用户可检索到不属于自己权限范围的知识内容。深层原因是 DC 在知识权限的五个层面均未建设：
① 权限模型缺失——知识按什么维度隔离（智能体实例/租户/部门/文档级）未定义
② 权限标记机制缺失——知识入库时无法打权限标签（人工标记/继承外部 ACL 均不支持）
③ 检索时权限过滤缺失——向量检索不做权限拦截，全量返回后无 post-filter
④ 与灵基用户体系未打通——DC 不知道当前检索用户的角色/部门/所属实例，无法做动态权限判断
⑤ 权限管理界面缺失——运营者无处配置"谁能看什么知识"的规则
应有能力
① 定义知识权限模型：支持按智能体实例隔离（基础）+ 按部门/角色/用户组细粒度标记（进阶）
② 知识入库时支持打权限标签：手动标记 / 基于上传来源自动继承 / 映射外部文档权限（如 SharePoint ACL）
③ 检索引擎支持 pre-filter 或 post-filter 的权限过滤，确保用户只能获取有权内容
④ DC 检索接口自动接收灵基用户身份信息（角色/部门/实例），无需调用方额外传递
⑤ 提供权限配置管理界面，支持批量规则（如"IT 部门可见 IT 类知识"）、实时生效、变更审计
为什么是标品问题
知识权限管控是企业级产品的基本安全要求。振兴有 3 条业务线（Tech GBS / People GBS / BP），知识必须隔离。且未来对接 SharePoint 后权限继承更复杂。这不是修一个检索 Bug 就能解决的——是一整套权限体系需要从零建设

04 待讨论（2 项）

#10Build 开发的应用仅支持部署到苍穹待讨论
现状
Build 开发的后端应用只能托管到苍穹平台，而苍穹有独立的许可体系和账号体系。灵基用户（多数非 ERP 用户）没有苍穹账号，无法访问部署在苍穹上的应用
应有能力
Build 应支持将应用部署到多种目标环境：苍穹（现有）/ 灵基自身轻量级应用托管 / 客户自有云服务器。应用身份验证应直接基于灵基用户体系，不强制依赖苍穹身份
为什么是标品问题
灵基的目标用户群远大于 ERP 用户群。Build 应用只能跑在苍穹上 = 使用者必须有苍穹身份 = 灵基适用场景被限制在 ERP 用户圈内
待讨论
需先确认：灵基应用托管能力是否已在规划中？苍穹绑定是否有架构层面的必要性？确认后再定优先级
#34苍穹不支持客户二开应用透出 MCP 供灵基调用待讨论
现状
客户在苍穹上有二次开发的业务应用（自定义接口），但苍穹不支持将这些接口暴露为 MCP。灵基智能体只能连接标品预置的 MCP，无法调用客户在苍穹上已有的业务能力
应有能力
苍穹应支持客户将二开接口注册/透出为标准 MCP Server，使灵基智能体可直接连接调用。或灵基侧提供适配网关对接苍穹非 MCP 接口并转换为 MCP 协议
为什么是标品问题
大量企业客户在苍穹上已有定制化业务应用。这些已有能力无法被灵基调用 = 客户要么重新开发（重复建设），要么放弃智能体连接已有业务——两者都不可接受
待讨论
推动方向需确认：① 苍穹提供"自定义 MCP 透出"？② 灵基提供"苍穹接口→MCP"适配网关？③ 两者结合？

05 消息与事件（1 项）

#31灵基缺少接收 MCP Server 主动推送自定义格式消息的平台能力P0
现状
灵基智能体连接 MCP Server 后仅支持"灵基发起请求→MCP 返回结果"的同步调用。MCP Server 无法在工单分配、答复、SLA 告警等后台事件发生时，主动向指定灵基用户/工作组/智能体实例推送自定义格式消息。后台事件无法可靠进入灵基 = 灵基不能成为唯一工作台
应有能力
① 标准消息/事件接入协议（已鉴权 MCP Server 可主动投递）
② 按用户/工作组/角色/智能体实例路由
③ 支持文本/通知/卡片/按钮等自定义消息 Schema，由 Work 渲染和交互
④ 消息队列/幂等/重试/离线补发/已读未读
⑤ 后台→智能体、智能体→智能体跨主体消息传递 + 权限审计
⑥ 消息到达后触发智能体自动执行预设动作（事件驱动），而非被动等用户打开才展示
为什么是标品问题
异步事件推送不是 HelpDesk 私有需求——审批待办、告警、任务分配等企业场景都需要。只有请求—响应 = 只能"用户问、系统答"，不能支撑持续运行的业务工作台
与项目边界
标品负责通用接入/路由/投递/审计；HelpDesk 仅定义具体业务事件和卡片
方案推进
已有详细三阶段方案（方案A事件触发代发 / 方案B原生消息 / 方案C待办页面兜底）。Harness 侧事件触发基础能力预计 821 上线 → 灵基消息与事件推送能力方案设计

07 开发范式与工具链（15 项）

#28端到端开发流程完全断裂（最关键系统性问题）P2
⚠️ 灵基 Build 走向生产级平台最根本的问题。开发者需在 5+ 工具/环境间反复切换，各环节零衔接。
产品设计 (Kiro)→ APPS (本地IDE→KDM)→ Skill (Build→Console→Work)→ 智能体 (Build→Console→Work)→ 应用 (苍穹→Build→苍穹上线→配MCP)→ 联调 (Work)
应有能力
终态：一站式项目工作空间。初阶：需求产物自动传递到开发；APPS/Skill/智能体/应用同一沙箱联调；发布有依赖感知和批量操作；环境切换有明确引导
为什么是标品问题
任何开发超过"单技能"复杂度的项目都会遇到完全相同的断裂。Build 从"演示工具"走向"生产级平台"的根本问题
方案推进
"开发测试一体化"已有两个方案对比（方案一按数据分态 vs 方案二按环境隔离），待决策拍板 → 开发测试一体化方案设计

应有能力

为什么是标品问题
"先上线才能测试"违反软件工程基本流程
方案推进
"开发测试一体化"方案直接回应此痛点——目标是让用户在 Build 内直接测试，不再依赖先上线 → 开发测试一体化方案设计
#17同名 Skill 测试静默覆盖线上版本P1

#18MCP Server 关联与知识挂载无法在 Build 中连贯完成P3

智能体四要素（提示词+技能+知识+外部连接）配置分散三模块 = 任何开发者都会割裂
#19技能/智能体没有版本管理P2 推进中

#20智能体实例创建对苍穹有不明确依赖P3
现状
创建实例需在苍穹新增 Bot，为何需要不明确
应有能力
澄清是否真的依赖苍穹；如不需则解耦；如需则灵基侧自动化
为什么是标品问题
与 #10 同一架构耦合问题
#21智能体创建 Skill 后缺乏同步批量发布P3
现状
智能体发布依赖 Skill 先发布，需手动逐个按顺序
应有能力
一键发布时自动检测并同步发布依赖 Skill
为什么是标品问题
依赖关系应由平台管理，手动管发布顺序不可持续
#22对话更换 Skill 后工作区未同步P3
现状
对话显示已成功更换 Skill，但工作区文件和配置没同步
应有能力
对话操作实时同步到工作区，所见即所得
为什么是标品问题
"对话驱动开发"的核心可靠性问题
#23技能在智能体中被修改后无法同步上线P2
现状
在智能体对话中改了技能，提交智能体时技能发不上去，需手动复制回技能源文件再单独提交
应有能力
修改自动同步回源文件，或提交时检测变更提示一起提交
为什么是标品问题
"手动复制"极易遗漏 = 线上运行旧版本而不自知 = 隐性 Bug 主要来源
#24文件修改后文件树无状态标记P3
现状
修改文件后左侧文件树无任何视觉标记
应有能力
类 Git 状态标记（已修改/未提交/待审核）
为什么是标品问题
无标记 = 靠记忆管理 = 复杂项目必遗漏
#25提交同名技能因名称重复失败P3
现状
修改后重新提交被视为"新建同名"而拒绝
应有能力
识别为"版本更新"；引入唯一 ID 区分新建与更新
为什么是标品问题
"更新已有技能"这个基本操作走不通
#29已发布技能更新内容后无法触发状态变更P2
现状
已发布技能无论直接改文件还是让 AI 改描述，都无法触发状态从"已发布"→"已保存"，导致无法重新提交。唯一 workaround 是让 AI 做无关改动才能触发
应有能力
文件内容变更后系统自动检测并标记为"已保存/待提交"
为什么是标品问题
"改了却提交不了" = 状态检测机制的基础 Bug
#30Build 不支持多人协同开发技能和智能体P2
现状
Build 单人单会话：① 无共享项目空间；② 技能只能聊天传文件；③ 接收方只能"删文件夹再上传"且触发 #29 Bug；④ 无变更合并；⑤ 无协作可见性
应有能力
① 共享项目空间（多人同一套制品）；② 标准技能交付流程（发布到项目/一键拉取）；③ 变更通知；④ 至少支持"分工→集成"模式
为什么是标品问题
任何超过一人做一个简单智能体的项目都需要协同。Build 无协同 = 只能做个人实验，无法支撑团队级项目
#33 不支持在 Build 中构建和调试MCP APPSP2
现状
MCP APPS 组件的开发必须在本地 IDE 中进行（编码→编译→打包），完成后手动上传到 KDM 平台注册。整个过程与 Build 完全割裂：Build 既不能创建 APPS 项目，也不能调试 APPS 组件，更无法在 Build 中将 APPS 与 Skill/智能体进行联调
应有能力
① Build 应支持 APPS 组件的创建、开发（或至少脚手架生成+本地开发引导）
② Build 中应能预览和调试 APPS 组件的渲染效果
③ APPS 组件发布后应能在 Build 中直接关联到 Skill/智能体，无需跳转 KDM 手动配置
④ 至少：Build 与本地 APPS 开发之间有自动化衔接（如 CLI 工具、热更新调试通道）
为什么是标品问题
APPS 是智能体与用户交互的核心层，但其开发与 Build 完全割裂 = Build 号称的"一站式开发"天然缺了交互层。开发者被迫在 Build（Skill/智能体）和本地 IDE（APPS）之间反复切换，这是 #28 端到端断裂在 APPS 维度的具体表现。关联：#1（规范开放）、#1b（上传入口）、本条（Build 中开发）三者需拉通
方案推进
已有完整方案设计，涵盖对话式创建/预览/构建打包/一键提交全流程，含任务拆解 → Build构建MCPAPPS方案设计
#11应用开发要求过多不相关文件权限P3
现状
Build 中开发应用时系统要求授予大量与当前开发任务不相关的文件权限
应有能力
最小权限原则，仅请求必需资源，权限用途有清晰说明
为什么是标品问题
违反安全原则，企业客户会触发安全审批流程、拖慢交付
