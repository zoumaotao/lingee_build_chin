02 MCP APPS 平台能力（6项）

#1APPS 不支持租户级自定义开发与发布上架 ❌ 未解决
当前现状
仅标品预置组件，不支持自定义
标品应有能力
支持开发者自定义 APPS 组件并发布到租户
为什么是标品问题
每个企业交互需求不同
#2APPS 与 LLM 数据传递仅支持全量消息，缺乏上下文精简机制 ❌ 未解决
当前现状
用户选 100 条数据必须全量塞入对话
标品应有能力
对话展示精简提示，实际数据静默更新 LLM 上下文
为什么是标品问题
Token 浪费 + 对话不可读 + 模型性能下降
#3APPS 组件渲染性能差，偶发渲染失败 ❌ 未解决
当前现状
滚动后组件被释放，回来重新渲染慢 / 偶发白屏
标品应有能力
合理缓存 + 状态恢复
为什么是标品问题
回看上文是高频操作
#4APPS 组件提交后不支持内容回显 ❌ 未解决
当前现状
提交后回看对话，已填内容消失
标品应有能力
数据持久化，回看可回显
为什么是标品问题
表单提交 → 回看是基本闭环
#5APPS 支持获取灵基登录用户信息 ✅ 已解决
当前现状
此前无法获取用户身份
标品应有能力
可获取用户 ID / 姓名 / 邮箱 / 部门
为什么是标品问题
几乎所有企业场景需要身份
#6Agent 无法感知 MCP APP 组件的内部业务逻辑 ❌ 未解决
当前现状
Agent 仅知道入参出参和名称描述
标品应有能力
结构化组件能力描述（JSON Schema）
为什么是标品问题
限制 AI 辅助开发上限

06 开发范式与工具链（12项）

#28端到端开发流程完全断裂（最关键问题） ❌ 未解决
⚠️ 这是灵基 Build 走向生产级平台最根本的问题。
当前开发者需在 5+ 个工具 / 环境间反复切换，各环节零衔接。

当前碎片化流程

产品设计 (Kiro) → MCP APPS (本地IDE→KDM) → Skill (Build→Console→Work) → 智能体 (Build→Console→Work) → 应用 (本地苍穹→Build→苍穹上线→配MCP) → 联调 (Work)
标品应有能力
终态：一站式工作空间
初阶：各环节自动化衔接
为什么是标品问题
Build 从"演示工具"走向"生产级开发平台"的根本问题
#16测试智能体必须先将其依赖的技能上线 ❌ 未解决
当前现状
开发阶段若要测试一个智能体，必须先将其依赖的技能走完"提交→审核→上线"的完整流程。技能未上线，智能体就无法调试
标品应有能力
开发态下智能体应能直接引用未上线的技能进行联调测试。"上线"是发布行为，不应成为"调试"的前置条件
为什么是标品问题
"先上线才能测试"违反软件工程基本流程（开发→测试→上线）。开发者被迫将未验证的技能上线，要么增加线上风险，要么严重拖慢迭代速度
#17构建同名 Skill 点击测试会静默覆盖线上 Skill ❌ 未解决
当前现状
开发者创建与线上 Skill 同名的新版本时，点击"测试"会直接覆盖线上正在运行的 Skill，无任何提醒或确认
标品应有能力
① 测试阶段：同名 Skill 的测试应在沙箱进行，不影响线上
② 上线阶段：检测到同名时明确提醒，让用户选择"更新现有版本"或"放弃"
为什么是标品问题
同名 Skill 在迭代更新中非常常见。平台缺乏冲突处理机制，静默覆盖线上版本可能导致生产环境故障
#18智能体的 MCP Server 关联与知识挂载无法在 Build 中连贯完成 ❌ 未解决
当前现状
① 智能体要连接的 MCP Server 需在 Console 中创建实例时关联，Build 中无法完成
② 智能体的知识也需在 Console 创建实例时关联
③ 知识同时又开放在 Work-智能体-知识中上传
开发者需在 Build → Console → Work 三处反复切换
标品应有能力
① 开发者在 Build 中一站式完成智能体全部配置（含 MCP Server 关联、知识挂载）
② 明确区分"开发者视角"和"运营者视角"的配置入口
为什么是标品问题
智能体 = 提示词 + 技能 + 知识 + 外部连接，四要素配置分散在三个模块。且开发者和运营者的操作混在一起，团队协作时必然混乱
#19智能体/技能没有版本管理 ❌ 未解决
当前现状
智能体/技能缺乏版本管理机制，无法查看历史版本、对比差异、回滚到之前的版本
标品应有能力
每次提交/上线形成版本快照，支持版本列表查看、Diff 对比、一键回滚
为什么是标品问题
智能体/技能在迭代中会频繁修改提示词、调整技能编排。没有版本管理意味着改坏了无法回滚、多人协作无法追溯变更——这是企业级开发平台的基本门槛
#20智能体实例创建对苍穹有不明确依赖 ❌ 未解决
当前现状
创建智能体实例时需在苍穹中新增一个 Bot 机器人，但为什么需要这步、具体需要什么权限均不明确
标品应有能力
① 先澄清：智能体实例创建是否真的需要依赖苍穹？不需要则解除耦合
② 如确需，应在灵基侧自动化完成，不要求开发者手动操作苍穹
为什么是标品问题
与 #10（应用部署强绑苍穹）属同一架构耦合问题。没有苍穹环境的团队将无法完成智能体部署
#21智能体创建 Skill 后缺乏同步批量发布机制 ❌ 未解决
当前现状
AI 辅助创建智能体时可能自动创建配套 Skill，但智能体发布依赖 Skill 先发布。开发者需手动按顺序逐个发布，极易遗漏
标品应有能力
一键发布智能体时，自动检测并同步发布其依赖的未上线 Skill（或至少提示并支持批量操作）
为什么是标品问题
智能体与 Skill 存在天然依赖关系，发布流程应感知这层依赖。手动管理发布顺序不可持续
#22Build 中通过对话更换 Agent 的 Skill 后工作区未同步 ❌ 未解决
当前现状
通过对话指令更换 Agent 绑定的 Skill 后，对话内容显示已成功，但工作区的实际文件和配置没有同步更新。需手动再操作一次
标品应有能力
对话式操作的结果应实时同步到工作区文件和配置中，保持所见即所得
为什么是标品问题
Build 的核心交互模式是"对话驱动开发"。如果对话中的操作不真实反映到工作区，开发者无法信任对话结果，对话式开发的可靠性被根本破坏
#23技能在智能体中被修改后无法同步上线 ❌ 未解决
当前现状
先独立开发技能，再在智能体中使用。本地文件结构是将技能拷贝到智能体目录下。若在智能体对话中修改了技能：
① 提交智能体时只能发布智能体本身，技能发不上去
② 需手动将修改复制回技能源文件
③ 再单独测试/提交技能
线上才是最新版本
标品应有能力
① 在智能体上下文中修改技能后，修改自动同步回技能源文件
② 或：提交智能体时检测技能有变更，提示一起提交
为什么是标品问题
在智能体中迭代修改技能是高频操作。"手动复制回源文件"极易遗漏，导致线上运行旧版本技能而开发者不自知——这是隐性线上 Bug 的主要来源
#24智能体 / 技能文件修改后文件树无状态标记 ❌ 未解决
当前现状
文件被修改后，左侧文件树中没有任何直观的状态标记（如已修改、未保存、未提交等）
标品应有能力
文件树应显示文件状态（类似 Git：已修改未保存、已保存未提交、已提交待审核等）
为什么是标品问题
多文件项目中需要快速识别变更范围。无状态标记意味着开发者只能靠记忆管理文件状态，复杂项目中极易遗漏提交
#25提交同名技能因名称重复失败，不支持更新语义 ❌ 未解决
当前现状
将修改后的技能重新提交到"个人使用"时，因名称重复而失败。系统将"修改后重新提交"等同于"新建同名"而拒绝
标品应有能力
① 修改后重新提交应识别为"版本更新"而非"新建"
② 引入除名称外的唯一标识（ID），区分新建与更新
为什么是标品问题
技能迭代更新是日常操作。当前机制让"更新已有技能"这个最基本的操作走不通，开发者被迫改名或先删旧版本
#26Build 使用 fast 模型时不定期进入死循环 ❌ 未解决
当前现状
在 Build 中使用 fast 模型进行对话开发时，模型会不定期进入死循环——反复输出相同内容或陷入无意义的循环调用，直到开发者手动终止
标品应有能力
模型服务应具备循环检测和自动中断机制，检测到重复输出时自动停止并提示用户
为什么是标品问题
模型服务是 Build 的底层基础设施。死循环浪费 Token 和开发时间，且终止后前序对话上下文可能丢失，开发者被迫重新开始
#27Build 使用 deep 模型时回复无限加载 ❌ 未解决
当前现状
使用 deep 模型时，AI 回复有时一直处于加载状态（无限加载动画），无法正常输出结果，只能点击"终止"
标品应有能力
应有超时检测和优雅降级机制：超时后提示用户可选重试或降级到其他模型
为什么是标品问题
deep 模型通常用于复杂的技能/智能体开发。若频繁卡死，开发者将被迫降级使用能力更弱的 fast 模型，影响开发质量
#29已发布技能更新内容后无法触发状态变更，导致无法重新提交 ❌ 未解决
当前现状
已发布的技能，无论是直接更新本地文件内容，还是在对话框中让 AI 修改描述，都无法触发状态从"已发布"变为"已保存"，导致无法重新提交。唯一 workaround 是让 AI 做无关改动（如改描述语言）才能触发状态变化
标品应有能力
技能文件内容变更后，系统应自动检测并标记为"已保存/待提交"
为什么是标品问题
"改了内容却提交不了"属于状态检测机制的基础 Bug
#30Build 不支持多人协同开发技能和智能体 ❌ 未解决
Build 当前只能单人单会话工作，完全没有团队协作机制。
当前现状
① 没有共享项目/工作空间——每人只能在自己的 Build 会话中工作
② 没有技能交付标准流程——开发好的技能只能通过聊天传文件
③ 接收方无标准导入方式——只能"删除本地文件夹再上传"，且触发 #29 状态 Bug
④ 没有变更合并机制——两人同时改同一制品时无法合并
⑤ 没有协作可见性——看不到其他人在做什么、改了什么
标品应有能力
① 共享项目空间：多人加入同一项目，共享同一套制品（智能体/技能/APPS）
② 标准交付流程：支持将技能"发布到项目"或"共享给协作者"，一键拉取最新版本
③ 变更感知：协作者更新后，其他人能收到通知或看到变更提示
④ 至少支持"分工→集成"：不同人负责不同技能，集成到同一智能体时有工具支持而非手动文件搬运
为什么是标品问题
任何超过"一人做一个简单智能体"的项目都需要多人协作。振兴 HelpDesk 就有多人分工（接口技能/问答技能/智能体编排各有负责人）。Build 无协同机制 = 只能用于个人实验，无法支撑团队级生产项目。这是从"个人工具"走向"团队开发平台"的关键缺失
