# 灵基平台「消息与事件推送」能力方案设计

> 背景：振兴 HelpDesk 项目需要实现"后台事件驱动灵基用户交互"的完整闭环  
> 来源：内部沟通记录整理  
> 状态：方案初稿，待各方对齐  
> 日期：2026-08-03

---

## 一、需求场景还原

振兴 HelpDesk 的完整业务流程如下：

```
用户提问 → AI问答未解决 → 自动创建工单 → 后台自动分配
→ 通知处理人（灵基内） → 处理人在灵基处理工单
→ 回复通知提单人（灵基内） → 提单人在灵基评价打分
→ SLA满意度数据回传后台
```

其中，客户能通过 Build 自行构建智能体+技能来实现"AI问答"和"创建工单"环节。但**后半段链路**卡在灵基平台能力缺失：

> **核心卡点：** 后台事件发生时（工单分配、答复、SLA告警），如何主动向灵基中指定用户/工作组推送消息，并支持用户在灵基内完成后续操作？

---

## 二、能力需求拆解

根据沟通记录，涉及以下三项平台能力（按优先级排列）：

### 能力 1：事件触发（Harness 侧）

**一句话：** 外部系统能通过 API 主动触发灵基智能体执行，并传递业务上下文。

| 子项 | 描述 | 当前状态 |
|------|------|---------|
| 1.1 智能体被外部触发执行 | 外部系统（工单后台）通过 API 调用，唤起指定智能体为指定用户运行一个任务 | 🟡 正在推进，预计 821 基础能力就绪 |
| 1.2 外部传入业务上下文 | 触发时可传入结构化参数（工单信息、负责人信息、提单人信息等），作为智能体本次执行的上下文 | 🟡 同上，需确认参数 Schema |
| 1.3 触发目标定位 | 支持指定"对哪个用户"触发（而非全局广播），如：通知工单处理人、通知提单人 | ⚪ 待确认是否 821 范围 |

**业务场景举例：**
- 工单分配后 → 触发"提单小助手智能体"向处理人推送工单详情
- 处理人回复后 → 触发智能体向提单人推送回复内容
- SLA 即将超时 → 触发告警推送给处理人/管理员

---

### 能力 2：向指定用户推送消息/通知（平台 Foundation 侧）

**一句话：** 后台服务能向灵基中指定用户发送消息或通知，用户在灵基内可感知并操作。

| 子项 | 描述 | 当前状态 |
|------|------|---------|
| 2.1 系统消息推送 API | 平台提供 Server-to-User 的消息推送接口，支持后台服务向指定用户 ID 发送消息 | 🔴 不支持，暂无产品负责人 |
| 2.2 消息格式可自定义 | 消息体支持自定义格式：标题、正文、操作按钮（如"查看详情""去处理"） | 🔴 同上 |
| 2.3 消息路由到正确位置 | 消息能出现在灵基 Work 的某个位置（通知中心 / 对话流 / 待办列表），用户不遗漏 | 🔴 同上 |
| 2.4 离线/未读补发 | 用户不在线时消息不丢失，上线后可收到 | 🔴 同上 |
| 2.5 消息关联操作入口 | 点击消息可跳转到对应智能体/页面继续操作（如进入工单处理对话） | 🔴 同上 |

**业务场景举例：**
- 工单分配后 → 向处理人发送消息："你有一个新工单待处理 [查看详情]"
- 处理人回复后 → 向提单人发送消息："你的工单已回复 [查看回复] [评价]"
- SLA 超时 → 向管理员发送告警："工单 #1234 已超时 [催办]"

---

### 能力 3：待办协作展示（平台 Work 侧）

**一句话：** 灵基 Work 中有一个"待办"入口，用户可以看到自己需要处理的事项，并从待办直接进入智能体操作。

| 子项 | 描述 | 当前状态 |
|------|------|---------|
| 3.1 Work 自定义菜单 | Work 下可挂载自定义菜单页面 | 🟢 应用菜单管理功能已上线 |
| 3.2 挂载第三方应用 | 菜单下可嵌入已部署好的第三方应用页面 | 🟢 当前已支持 |
| 3.3 挂载 Build 构建的应用 | 菜单下可嵌入 Build 中创建的应用 | 🟡 需先解决 Build 应用的部署问题 |
| 3.4 待办列表页面 | 展示当前用户待处理的工单/任务列表 | 🟡 建议客户自建页面挂载到 Work 菜单 |
| 3.5 从待办跳转到智能体 | 点击待办项可打开对应智能体对话，并自动带入工单上下文 | ⚪ 依赖能力 1 的"外部触发+上下文传入" |

**当前可行方案（Work 自定义菜单）：**
- 客户自行开发一个"待办列表"前端页面
- 通过 Work 菜单管理功能挂载到灵基 Work
- 页面内调用工单后台 API 获取待办数据并展示
- 点击待办项时，如需进入智能体，依赖能力 1 的触发机制

## 三、端到端流程 × 能力映射

下面将业务流程的每一步与所需平台能力对应：

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 步骤                        │ 实现方式              │ 依赖能力          │
├────────────────────────────────────────────────────────────────────────────┤
│ 1. 用户提问                 │ 灵基 Work 对话        │ 已有              │
│ 2. AI知识问答               │ 智能体 + DC 知识检索  │ 已有              │
│ 3. 问答未解决→创建工单      │ 智能体 Skill + MCP    │ 已有              │
│ 4. 后台自动分配工单         │ 工单后台业务逻辑      │ 客户自建          │
│ 5. 通知处理人"有新工单"     │ 推送消息到处理人      │ 能力1 + 能力2     │ ⬅️ 卡点
│ 6. 处理人查看待办           │ Work菜单内待办页      │ 能力3             │
│ 7. 处理人进入智能体处理     │ 触发智能体+上下文     │ 能力1             │ ⬅️ 卡点
│ 8. 处理人回复               │ 智能体 Skill + MCP    │ 已有              │
│ 9. 通知提单人"已回复"       │ 推送消息到提单人      │ 能力1 + 能力2     │ ⬅️ 卡点
│ 10. 提单人评价打分          │ 智能体对话/APPS卡片   │ 已有              │
│ 11. SLA 数据回传后台        │ MCP 调用             │ 已有              │
└────────────────────────────────────────────────────────────────────────────┘
```

**总结：** 步骤 5、7、9 是卡点，核心依赖"事件触发"和"消息推送"两项平台能力。

## 四、能力覆盖关系分析：能力 3 能否替代能力 2？

### 结论：POC 阶段可以用能力 3 暂时覆盖能力 2，但有边界

| 维度 | 能力 3（待办页面）能做到 | 能力 3 做不到（仍需能力 2） |
|------|------------------------|---------------------------|
| 信息展示 | ✅ 待办页面展示新工单/新回复/待评价 | — |
| 操作入口 | ✅ 从待办点击进入智能体处理 | — |
| 主动触达 | ？ | 用户不打开页面就不知道有新消息，无红点/推送 |
| 实时性 | ？ | 工单分配后处理人不会"被通知到"，只能自己刷 |
| 离线场景 | ？ | 用户下次上线无明确提示"你有 N 条新待办" |

### 一期阶段建议方案

振兴的处理人是 20-30 名专职坐席，可以养成"开工先看待办"的工作习惯。在 POC 阶段：

- **能力 3（待办页面）** 承担"信息展示 + 操作入口"的职责
- 配合能力 1（事件触发），待办页面可通过**轮询或长连接**获取最新数据，减少感知延迟
- 能力 2（系统消息推送）推迟到正式上线阶段

### 如果客户要求"实时通知到人"

POC 阶段有两个变通方案：

| 变通方案 | 做法 | 优缺点 |
|---------|------|--------|
| 方案 A：智能体代发 | 事件触发智能体 → 智能体向目标用户发起对话 | 无需新平台能力，但体验是"对话"而非"通知" |
| 方案B：外部渠道补充 | 工单后台同时发邮件/企微通知 | 不依赖灵基，但体验割裂、用户需跳转 |

### ⚠️ 需与客户确认

> **一期阶段是否接受"处理人主动查看待办"的模式？**  
> - 如果接受 → 能力 3 够用，能力 2 可推到正式上线  
> - 如果不接受 → 短期走方案 A（事件触发+智能体代发）或方案B（外部渠道通知）

## 五、技术方案建议

### 5.1 方案 A：事件触发 + 智能体代发消息（短期可行）

利用 821 即将上线的"事件触发"能力，绕过"系统消息"的缺失：

```
工单后台（事件发生）
    ↓ 调用灵基 API：触发指定智能体，传入上下文
灵基 Harness 执行智能体
    ↓ 智能体以"系统角色"向目标用户发起对话
目标用户在 Work 中收到智能体对话消息
    ↓ 用户在对话中操作（查看/处理/评价）
```

**优点：** 不需要等"系统消息"能力开发，821 事件触发上线后即可实现
**缺点：** 用户收到的是"智能体对话"而非"通知"，体验不如原生消息；依赖事件触发能力支持"对指定用户触发"

### 5.2 方案 B：原生系统消息 + 跳转入口（长期理想态）

平台提供完整的消息推送基础设施：

```
工单后台（事件发生）
    ↓ 调用灵基消息推送 API
灵基消息中心
    ↓ 路由到目标用户
用户在 Work 中收到通知（红点/消息列表）
    ↓ 点击通知中的操作按钮
跳转到对应智能体对话（自动带入上下文）
```

**优点：** 体验原生、不依赖智能体运行时
**缺点：** 系统消息能力目前无人负责，上线时间不可控

### 5.3 方案 C：能力 3 待办页面兜底（POC 最小可行）

如果客户接受"处理人主动查看待办"模式，POC 阶段最简方案：

```
工单后台（事件发生）
    ↓ 写入工单状态变更到数据库
待办页面（Work 菜单中）
    ↓ 轮询/长连接获取最新待办列表
处理人打开 Work → 看到待办 → 点击进入智能体处理
```

**优点：** 不依赖任何新平台能力（事件触发、系统消息均不需要），客户完全自建可控  
**缺点：** 无主动通知，依赖用户习惯；感知延迟取决于轮询频率  
**适用：** POC 验证业务流程可行性，后续再叠加通知能力提升体验

### 5.4 建议实施路径（更新）

| 阶段 | 时间 | 方案 | 备注 |
|------|------|------|------|
| POC 阶段（最小化） | 现在即可启动 | 方案 C（待办页面兜底） | 客户自建待办页挂 Work 菜单，验证业务流程 |
| POC 阶段（增强） | 821 后 | 方案 A（事件触发代发） | 叠加主动通知能力，处理人不用自己刷 |
| 正式上线 | 待排期 | 方案 B（原生消息） | 需产品设计+开发排期 |
