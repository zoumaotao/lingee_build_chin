Build 构建 MCP APPS 方案设计

用户通过对话即可完成 APPS 的创建、开发、调试、测试和发布

面向：Build产品团队、Console团队、MCP APPS平台团队 状态：方案初稿

一、背景与目标

1.1 当前现状与问题

MCP APPS 是灵基智能体与用户之间的可视化交互层，当前开发流程如下：

#问题影响
1APPS 开发完全在本地 IDE，与 Build 割裂Build 号称"一站式开发"但缺了交互层
2上传入口在 KDManage，客户无法自助每次变更都要走金蝶内部流程
3Build 中做 Skill/智能体时无法同步做 APPS交互层和逻辑层开发完全分离
4开发者需在 5+ 工具间切换IDE→KDManage→Build→Console→Work
5无版本管理修改后无法回滚、无法对比

1.2 目标

一句话目标：用户在 Build 中通过对话就能完成 MCP APPS 的创建、开发、调试、测试和发布——与技能开发、智能体开发一样的"对话即开发"体验。

1.3 MCP 开发的子类型

MCP 开发涵盖两类不同性质的制品：

子类型产物本质本方案覆盖
MCP APPS（交互式）前端 UI 组件（React/Vue → zip）对话中的可交互卡片（表单、列表、图表等）✅ 本方案聚焦
MCP Tool（工具式）后端服务（Python/Java/TS → 容器部署）给智能体调用的 API 能力（数据读写、业务逻辑）⏳ 后续单独设计
两者关系：APPS 是"前端展示层"，MCP Tool 是"后端能力层"。APPS 通过 callServerTool 调用 MCP Tool 完成实际业务操作。一个完整的 MCP 场景通常需要两者配合（如工单确认卡 APPS + Create_Ticket Tool）。

本方案聚焦 MCP APPS（交互式），MCP Tool 的 Build 开发能力后续单独设计。

二、MCP APPS 当前机制完整介绍

2.1 什么是 MCP APPS

MCP APPS 是灵基智能体对话中嵌入的自定义可交互 UI 组件（如表单卡片、数据列表、图表等）。它运行在沙箱 iframe 中，通过 AppBridge（基于 PostMessage）与宿主（灵基 WebUI）双向通信。

核心定位：智能体与用户之间的"可视化交互层"——让对话不仅有文字，还有结构化的表单、按钮、列表等 UI 形态。

2.3 通信能力

Host → App（宿主向组件注入数据）：

能力方法说明

2.7 本地调试机制

开发者本地启动 dev server 后，通过 URL 参数将 App 资源指向本地：

https://your-webui.com/session/xxx?lg_mcpapp_cdn=http://localhost:4000
原理：Host 加载 App 资源时检查 lg_mcpapp_cdn 参数，如存在则将 CDN 地址替换为该参数值。

2.8 当前 KDManage 上架流程

⚠️ 该入口仅金蝶内部人员可操作，租户/客户无法访问 KDManage。
  1. 登录 KDManage → 左侧菜单 → 业务组件
  2. 新建业务组件
  3. 上传 zip 文件（打包好的 APPS）
  4. 配置集群连接器
  5. 关联集群连接器里的 MCP 工具
  6. 提交保存、审核上架

3.1 整体开发流程

“测试”按钮交互约束：点击后上传当前合格 MCP App 制品到沙箱，并始终停留在当前 Build 页面，不打开或跳转沙箱 Work。当前修订合格但未打包时，本次点击可显式触发构建打包；无用户动作时不得后台上传。只有 Console 返回与当前修订、构建和制品哈希匹配的真实成功回执后，才在原页显示绿色提示：已经上传到沙箱，您可以开始制作技能进行测试。失败、超时、接口不可用或回执不匹配时保留产物和错误并允许重试，不得显示成功。上传成功只表示沙箱资源已就绪，不代表 Skill 已制作、端到端测试通过或生产发布成功。

3.3 与其他开发能力的协同

与技能开发的协同

• APPS 通过 appCode 被 Skill 的 allowed-tools 引用
• Build 生成 APPS 时自动生成配套 SKILL.md
• 在 Skill 开发中发现需要 UI 时，可切换到 APPS 开发上下文

与智能体开发的协同

• 智能体通过 Skill 间接使用 APPS
• 测试智能体时 APPS 在沙箱 Work 中正常渲染
• 一个项目可包含 APPS + Skill + 智能体

依赖感知

• 如果 Skill 引用了未提交的 APPS
• Build 在测试前自动先将 APPS 提交到沙箱 Console
• 确保联调可用

七、端到端流程设计

5.1 目标流程全景

5.2 关键链路 A：MCP APPS 独立开发

适用场景：用户专门要开发一个 APPS 组件，之后再在 Skill/智能体中引用。

1. 用户进入 Build，选择"MCP 开发"，开始新会话
2. 用户用自然语言描述需求
3. Build 澄清需求，确认后生成项目代码
4. 用户通过对话迭代修改 + 预览确认
5. 用户点击“测试”
    └── Build 保持当前页面；如需则 vite build → zip → 上传沙箱 Console
    └── 仅真实回执匹配当前制品后，原页绿色显示“已经上传到沙箱，您可以开始制作技能进行测试”
6. 用户继续在 Build 制作/关联 Skill；需要完整联调时再显式发起 Skill 测试
    └── 对话 → Skill → APPS 渲染 → 用户交互 → MCP Tool 调用 → 结果
7. 验证通过，用户点击“提交生产”
    └── Build 构建打包 → 提交生产 Console → 进入审核流程
8. 管理员审核上架
9. 生产 Work 中智能体可使用该 APPS 组件 ✓

5.3 关键链路 B：与 Skill 一体化开发

适用场景：用户在开发 Skill 过程中，发现需要一个自定义 APPS 来承载交互。

1. 用户在 Build 中开发 Skill（技能开发模式）
2. 用户描述 Skill 需要展示一个自定义 UI 卡片
3. Build 识别需要创建 APPS，切换到 APPS 开发上下文
4. Build 澄清 APPS 需求，生成代码
5. 用户确认后，Build 自动将 APPS 的 appCode 写入 Skill 的 allowed-tools
6. 用户点击 Skill 的“测试”
    └── Build 检测到 Skill 依赖尚未在沙箱就绪的 APPS
    └── Build 自动先上传 APPS 并核对真实回执
    └── 再将 Skill 提交到沙箱；依赖已就绪时复用回执
7. Build 保持当前页面并展示测试入口/执行状态，不自动跳转沙箱 Work
8. 一体化提交：APPS + Skill 按依赖顺序提交生产
依赖感知规则：如果 Skill 引用了本项目中尚未在沙箱就绪的 APPS，Build 必须在 Skill 测试前自动先上传 APPS，否则测试运行时无法加载该组件。APPS Builder 自身的“测试”按钮只准备沙箱资源并原页反馈，不等于 Skill 测试或端到端测试通过。

5.4 Skill 端到端联调流程（沙箱资源就绪后的独立动作）

APPS 开发者先在 Build 点击“测试”完成沙箱上传；真实回执校验后原页绿色提示且不跳转。随后继续制作/关联 Skill，并由用户显式发起 Skill 测试。下图描述的是后续 Skill 运行链路，不是 APPS“测试”按钮点击后的自动跳转。

八、APPS 项目结构与规范

6.1 项目文件结构

在 Build 中创建 MCP APPS 项目时，自动生成以下标准结构：

my-helpdesk-ticket-card/ ├── src/ │ ├── App.tsx ← 主组件（开发者编写的 UI 逻辑） │ ├── main.tsx ← 入口文件（SDK 初始化，不需要改） │ └── styles.css ← 样式文件 ├── public/ │ └── (静态资源) ├── dist/ ← 构建产物（build 后生成） │ └── index.html ├── info.json ← 组件元信息（appCode/relateTools/entryTool等） ├── SKILL.md ← 配套 Skill 描述文件 ├── package.json ← 依赖管理 ├── vite.config.ts ← 构建配置 └── mcp-app.config.json ← 本地调试配置（可选）

6.2 info.json 关键字段

字段说明示例
appCode组件唯一编码（发布后不可改）chin_helpdesk_ticket_confirm
appName组件名称工单确认卡
description组件描述展示工单草稿，支持编辑确认后提交
mcpConnector关联的 MCP 集群连接器{ "type": "OTHERS", "code": "chin_mcp" }
relateTools组件需要调用的 MCP 工具列表[{ "name": "Create_Ticket" }]
entryTool.virtual虚拟入口工具的输入/输出 Schema描述组件接受什么参数
runMode运行模式"message"（对话内）或 "sidecar"（侧边栏）
version版本号"1.0.0"

6.3 SKILL.md 配套规范

每个 APPS 组件应配套一个 SKILL.md，Build 在生成 APPS 时自动生成：

--- name: {skill-name} description: Use this skill to open the managed MCP App {appName}. allowed-tools: - {appCode} --- # {组件名称} Use this skill when the user asks to {触发场景描述}. Call the MCP tool `{appCode}` with the following arguments: - {参数1}: {说明} - {参数2}: {说明}

十、与现有机制的兼容

现有机制方案兼容策略
本地 IDE 开发 + zip 上传继续支持。Build 只是新增了一条"对话即开发"路径，不取代本地开发方式
KDManage 上传KDManage 作为金蝶内部管理工具继续存在。Console 是面向租户的开放入口
lg_mcpapp_cdn 本地调试Build 的预览功能内置了类似机制，无需手动加 URL 参数
info.json 规范完全复用现有规范，Build 只是通过对话辅助生成和编辑
@modelcontextprotocol/ext-apps SDK完全复用，Build 项目模板中直接引入
SKILL.md 格式完全复用，Build 在生成 APPS 时自动生成配套 SKILL.md
现有已上架组件不受影响，Console 组件仓库中的已有组件继续可用

十二、风险与待确认项

#风险/待确认影响建议
1Build 是否具备运行 vite 的能力决定构建方式无法运行则改为服务端构建
2Console 沙箱上传 API 的鉴权、权限、幂等和真实回执字段决定能否安全展示“已经上传到沙箱”未确认或回执不完整时失败关闭，不能本地假成功
3预览是否支持真实 MCP Tool 调用预览深度分两级：mock预览 + 真实联调
4APPS 引用的 Tool 是否必须已存在开发体验预览允许mock，提交时校验
5APPS + Skill 发布顺序依赖一体化发布Build感知依赖，自动先提交APPS
6对话式代码生成质量APPS可靠性预览作为质量门禁+模板降低自由度
7多人协作编辑冲突初期不支持，后续结合版本管理

5组件启停控制appCode + 操作（启用/停用/下架）操作结果Console 管理界面使用
6生产组件提交zip + 租户 + appCode + artifactSha256 + 生产提交幂等键submissionId、审核状态、request ID与沙箱上传记录和权限隔离
