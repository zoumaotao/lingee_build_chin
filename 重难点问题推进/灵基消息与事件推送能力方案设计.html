灵基平台「消息与事件推送」能力方案设计

状态：方案初稿 日期：2026-08-03 来源：内部沟通记录整理

01 需求场景还原

振兴 HelpDesk 的完整业务流程如下，其中后半段链路卡在灵基平台能力缺失：

🚨 核心卡点：后台事件发生时（工单分配、答复、SLA告警），如何主动向灵基中指定用户/工作组推送消息，并支持用户在灵基内完成后续操作？

02 能力需求拆解

根据沟通记录，涉及以下三项平台能力（按优先级排列）：

能力1：事件触发
🟡 推进中

Harness 侧

外部系统能通过 API 主动触发灵基智能体执行，并传递业务上下文。

能力2：消息推送
🔴 不支持

Foundation 侧

后台服务能向灵基中指定用户发送消息或通知，用户在灵基内可感知并操作。

能力3：待办协作展示
🟢/🟡 部分就绪

Work 侧

灵基 Work 中有"待办"入口，用户可看到需处理事项，并从待办进入智能体操作。

能力1：事件触发（Harness 侧）

子项描述当前状态
1.1 智能体被外部触发执行外部系统通过 API 调用，唤起指定智能体为指定用户运行任务🟡 推进中，预计 821 就绪
1.2 外部传入业务上下文触发时传入结构化参数（工单信息、负责人信息等）作为执行上下文🟡 同上，需确认参数 Schema
1.3 触发目标定位支持指定"对哪个用户"触发（而非全局广播）⚪ 待确认是否 821 范围

能力2：向指定用户推送消息/通知（Foundation 侧）

子项描述当前状态
2.1 系统消息推送 APIServer-to-User 消息推送接口，支持向指定用户 ID 发送消息🔴 不支持，暂无产品负责人
2.2 消息格式可自定义支持标题、正文、操作按钮（"查看详情""去处理"）🔴 同上
2.3 消息路由到正确位置出现在通知中心/对话流/待办列表，用户不遗漏🔴 同上
2.4 离线/未读补发用户不在线时消息不丢失，上线后可收到🔴 同上
2.5 消息关联操作入口点击消息可跳转到对应智能体/页面继续操作🔴 同上

能力3：待办协作展示（Work 侧）

子项描述当前状态
3.1 Work 自定义菜单Work 下可挂载自定义菜单页面🟢 已上线
3.2 挂载第三方应用菜单下可嵌入已部署好的第三方应用页面🟢 已支持
3.3 挂载 Build 构建的应用菜单下可嵌入 Build 中创建的应用🟡 需先解决 Build 部署问题
3.4 待办列表页面展示当前用户待处理的工单/任务列表🟡 建议客户自建页面挂载
3.5 从待办跳转到智能体点击待办项打开对应智能体对话，自动带入上下文⚪ 依赖能力1"事件触发+上下文传入"

04 能力覆盖关系分析

能力3 能否替代能力2？

结论：POC 阶段可以用能力3 暂时覆盖能力2，但有边界。

维度能力3（待办页面）能做到 ✅能力3 做不到（仍需能力2）❌
信息展示✅ 待办页面展示新工单/新回复/待评价—
操作入口✅ 从待办点击进入智能体处理—
主动触达—❌ 用户不打开页面就不知道有新消息，无红点/推送
实时性—❌ 工单分配后处理人不会"被通知到"，只能自己刷
离线场景—❌ 用户下次上线无明确提示"你有 N 条新待办"

💡 一期阶段建议：振兴的处理人是 20-30 名专职坐席，可以养成"开工先看待办"的工作习惯。

  • 能力3（待办页面） 承担"信息展示 + 操作入口"的职责
  • 配合能力1（事件触发），待办页面可通过轮询或长连接获取最新数据
  • 能力2（系统消息推送）推迟到正式上线阶段

如果客户要求"实时通知到人"

变通方案做法优缺点
方案A：智能体代发事件触发智能体 → 智能体向目标用户发起对话无需新平台能力，但体验是"对话"而非"通知"
方案B：外部渠道补充工单后台同时发邮件/企微通知不依赖灵基，但体验割裂、需跳转
⚠️ 需与客户确认的关键决策：

一期阶段是否接受"处理人主动查看待办"的模式？

  • 如果接受 → 能力3 够用，能力2 可推到正式上线
  • 如果不接受 → 短期走方案A（事件触发+智能体代发）或方案B（外部渠道通知）

05 技术方案建议

🅰️ 方案A：事件触发 + 智能体代发消息 短期可行

利用 821 即将上线的"事件触发"能力，绕过"系统消息"的缺失。

🅱️ 方案B：原生系统消息 + 跳转入口 长期理想态

平台提供完整的消息推送基础设施。

🅲 方案C：待办页面兜底 POC 最小可行

如果客户接受"处理人主动查看待办"模式，POC 阶段最简方案。

建议实施路径

阶段时间方案备注
POC 最小化 现在即可启动 方案C（待办页面兜底） 客户自建待办页挂 Work 菜单，验证业务流程
POC 增强 821 后 方案A（事件触发代发） 叠加主动通知能力，处理人不用自己刷
正式上线 待排期 方案B（原生消息） 需产品设计 + 开发排期

06 对各方的需求（Action Items）

6.1 对 Harness 团队

#需求优先级期望时间备注
H1提供外部触发 API（REST），支持传入目标用户 ID + 智能体 ID + 业务参数P0821核心卡点
H2触发时支持传入结构化上下文（JSON），智能体执行时可读取P0821工单信息等
H3确认触发 API 的鉴权方式（API Key / OAuth / 签名）P0821客户后台需对接
H4支持"对指定用户"触发（而非全局/无状态触发）P0821不同工单通知不同人
H5提供触发 API 的接口文档和 SDK 示例P1821客户对接用

6.2 对平台 Foundation 团队

#需求优先级期望时间备注
F1系统消息推送 API 的产品设计P1待排期需找到产品负责人
F2消息格式规范定义（标题/正文/按钮/跳转链接）P1待排期—
F3消息存储 + 离线补发 + 已读未读P2待排期—
F4用户端消息展示入口（通知中心/红点提醒）P2待排期—

6.3 对 Build / Work 团队

#需求优先级期望时间备注
W1确认 Build 应用的部署方案（解决挂载到 Work 菜单的前置问题）P1近期部伟老师清楚细节
W2Work 菜单跳转到智能体对话时，支持传入初始上下文/参数P1821后从待办进入处理

6.4 对客户（振兴）

#需求说明
C1工单后台需实现 Webhook/事件回调机制工单状态变化时调用灵基触发 API
C2自行开发"待办列表"前端页面挂载到 Work 菜单
C3配合对接事件触发 API821 上线后联调
