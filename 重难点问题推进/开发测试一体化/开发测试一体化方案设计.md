# 开发测试一体化方案设计

> 定位：解决灵基 Build 开发与测试流程割裂的核心痛点  
> 来源：LINGEE BUILD · WHY CHANGE（01/02）+ MAKE THE CALL（02/02）  
> 状态：方案对比阶段，待决策

---

## 一、现在最大的痛：能开发、能测试，但两件事没连起来

**核心问题：** 问题不在于少一个"测试"按钮，而在于每测一次，用户都要自己搬运上下文、自己判断环境。

### 1.1 现在用户是这样干活的

```
在 Build        点击测试       看执行过程        回到 Build       Build 再修改      继续跳转
开发/修改  ──→  跳到 Work  ──→  找哪里有问题  ──→  重新描述一遍  ──→  智能体配置  ──→  再测一轮
  沙箱                                                                              
```

> 每轮优化都要"人肉搬运"测试结果。

### 1.2 四大痛点

| # | 关键词 | 痛点描述 | 影响 |
|---|--------|---------|------|
| 01 | **断** | 开发在 Build，测试在 Work，上下文割裂 | 测试过程中，工具调用和报错信息不能直接跳回 Build。用户发现问题后，还要自己总结一遍，再回 Build 描述修改要求。 |
| 02 | **缺** | Build 无法调用 Console 配置的真实 MCP 服务 | 智能体不调用企业 MCP，就无法验证真实业务场景。要实现开发测试一体化，需要 Build 开放测试 MCP 服务调用。 |
| 03 | **乱** | 环境切来切去，用户容易搞混 | Chat、Work 平时都在生产环境，Build 测试却要去沙箱；客户端又不能多开，用户很难一直记住自己现在在一个什么环境。 |
| 04 | **偏** | Build 与 Work 的 Harness 不是同一套 | 两边的运行链路和能力存在差异。可能出现 Build 测试没问题，发布到 Work 后效果却不一样。测试结果不能完全代表生产效果。 |

### 1.3 我们真正要实现的

> **用户一直留在 Build，测试过程自动变成下一轮优化的上下文。** 用户无须知道背后切了哪个环境。

目标流程：

```
开发/修改          直接测试        执行过程自动回传        继续优化         验证后发布到 Work
自然语言调整  ──→  在Build内发起  ──→  MCP、参数、结果、   ──→  不用人工复述  ──→  切换为生产MCP
智能体                              报错都带回来
```

### 1.4 核心问题（需要拍板）

> **开发测试用的 MCP 到底是放在生产 Foundation 里按"开发态"管理，还是让 Build 自动去开发测试环境里拿？**

由此形成下面两个方案。

---

## 二、两个方案怎么选：一个用户更好懂，一个安全边界更清楚

**核心差别：** 开发态 MCP 是放在 Console 生产环境里做数据区分，还是让 Build 生产环境自动转连 Console 沙箱环境。

---

### 方案一：Console 生产环境按数据分态 — MCP 服务按开发态/生产态管理

**用户更好理解**

**说人话：** Build 生产环境还是连接 Console 生产环境，只是在同一套 MCP 管理中，把测试用和正式用的 MCP 数据区分开。

#### 流程

```
开发测试        Build 生产环境  ──→  Console 生产环境  ──→  企业测试系统
怎么跑                              (开发态 MCP 配置)

发布以后        Work 生产环境  ──→  Console 生产环境  ──→  企业生产系统
怎么跑                              (生产态 MCP 配置)
```

#### 具体怎么做

1. Console 生产环境增加"开发态 MCP"标识，专门给 Build 开发测试使用
2. 开发态与生产态 MCP 分别配置测试/生产地址和密钥，Build 测试只能获取开发态
3. 发布后，智能体在 Work 中改用对应的生产态 MCP

#### 好在哪里

| 优点 |
|------|
| ✅ 环境一一对应：Build 生产环境对应 Console 生产环境 |
| ✅ 只做 MCP 数据区分，使用逻辑不变，用户理解成本小 |

#### 代价 / 风险

| 风险 |
|------|
| ✗ Console 生产环境要在 Build 下发开发态 MCP 服务能力 |
| ✗ 权限划分需清晰，否则容易混用导致生产环境被安全质疑 |

---

### 方案二：Console MCP 不分态 — 直接按 Console 环境隔离

**安全边界更清楚**

**说人话：** Console 里不再区分开发态和生产态 MCP。用户从 Build 生产环境发起测试时，后台自动转连 Console 沙箱环境。

#### 流程

```
开发测试        Build 生产环境  ──→  Console 沙箱环境  ──→  企业测试系统
怎么跑                              (自动转连)
                                    (沙箱 MCP 配置)

发布以后        Work 生产环境  ──→  Console 生产环境  ──→  企业生产系统
怎么跑                              (生产 MCP 配置)
```

#### 具体怎么做

1. Build 生产环境自动获取沙箱身份，并转连 Console 沙箱环境，用户尽量无感
2. 智能体、技能和 MCP 服务资源先在沙箱配置，开发测试调用沙箱 MCP
3. 验证通过后，再把智能体及相关配置发布到 Console 生产环境供 Work 使用

#### 好在哪里

| 优点 |
|------|
| ✅ 开发测试与生产完全隔离，MCP 密钥等不需要互通 Build |
| ✅ 即使开发中的智能体出错也不影响生产数据 |

#### 代价 / 风险

| 风险 |
|------|
| ✗ 要解决的环境连通问题更多：网络、资源 MCP 配置不互通 Build |
| ✗ Build 生产环境对应 Console 沙箱，MCP 资源要先让沙箱有 |
| ✗ 意味着维护两套环境体验出错，代价更大 |
| ✗ 用户理解成本较大，用户需要先去沙箱配资源 |

---

## 三、建议结论

| 视角 | 建议 |
|------|------|
| **从 Build 用户认知和使用习惯看** | **建议方案一。** 环境对应关系直观，用户只需要理解 MCP 有开发和生产之分。 |
| **从严格控制安全风险看** | **建议方案二。** 开发测试与生产环境彻底隔开，生产密钥不进入 Build 链路。 |

## 四、与其他重难点问题的关联

### 4.1 与 Build 构建 MCP APPS 方案的关联

| 关联点 | 说明 |
|--------|------|
| APPS 沙箱测试 | MCP APPS 开发流程中的"沙箱测试"环节，本质就是需要调用真实/测试态 MCP Tool。本方案决定了 APPS 联调时走哪条环境链路。 |
| 一键提交 | MCP APPS 的"提交到沙箱 Console"操作，方案一=在生产 Console 做开发态标记，方案二=真的提交到沙箱 Console 环境。 |
| 依赖感知 | Build 感知 Skill 对 APPS 的依赖后自动先提交 APPS，提交到哪个环境取决于本方案选择。 |

### 4.2 与版本管理方案的关联

| 关联点 | 说明 |
|--------|------|
| 版本状态流转 | "编辑中"状态的制品在测试时，是否需要先保存一个开发版本？测试通过后发布是否自动升版本号？ |
| 发布环境指纹 | 发布版本快照中需要记录"使用的是开发态 MCP 还是生产态 MCP"，方便回溯。 |
| 回滚联动 | 如果智能体回滚了版本，对应的 MCP 配置（开发态/生产态映射）是否也需要联动回滚？ |

### 4.3 与消息与事件推送能力的关联

| 关联点 | 说明 |
|--------|------|
| 测试结果回传 | "执行过程自动回传"能力本质上需要一套事件/消息通道，将 Work/沙箱中的执行结果推回 Build 上下文。 |
| 环境切换通知 | 方案二中 Build 自动转连沙箱，切换过程是否需要通过事件推送通知用户？ |

| 1 | Build 生产环境是否已有能力连接 Console 沙箱环境的网络通道？ | 方案二可行性前提 | 基础设施团队 |

| 5 | Build 内发起测试时，Harness 用的是 Build 内置的还是 Work 的？如果是内置的，与 Work 的 Harness 能力差异有多大？ | 痛点 04（测试结果偏差）能否解决 | Harness 团队 |
| 6 | 两个方案下，开发者在 Build 中发起测试后，是在 Build 内嵌 Work 沙箱窗口？还是跳转到外部 Work？ | 用户体验（痛点 03"乱"能否解决） | Build 产品团队 |

| 8 | 客户（如振兴）的企业 MCP 服务是否支持提供"测试实例"？如果客户只有一套 MCP 后端，两个方案的"测试态"都只是逻辑隔离？ | 方案实际效果 | 客户/项目经理 |
