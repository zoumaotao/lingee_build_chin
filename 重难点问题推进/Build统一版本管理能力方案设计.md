# Build 统一版本管理能力方案设计

> 定位：灵基 Build 全制品类型的版本管理能力顶层设计  
> 面向：Build 产品团队、Harness 团队、Console 团队  
> 状态：方案初稿，待评审  
> 日期：2026-08-03

---

## 一、问题定义

### 1.1 现状

灵基 Build 当前对所有制品类型（智能体、Skill、应用、MCP APPS、MCP Server）的存储机制是：**每次保存直接覆盖上一次，无任何历史记录。**

这意味着：
- 开发者误操作无法回退
- 无法对比"上次能跑的版本"和"这次改坏的版本"
- 发布到 Work 后发现问题无法回滚
- AI 自动生成代码后，人无法审查"改了什么"
- 多人协作（如果有）会互相覆盖
- 无法满足企业级审计要求（谁、什么时候、改了什么）

### 1.2 客户真实需求（振兴集团提出）

> **原始需求：** Skill 需要支持研发版本化。发布出去的 Skill/Agent 在重新编辑重新发布后，状态需要调整，体现已被重新编辑，而不是停留在"已发布"。再次发布后，版本编号需要跟上次有差异。

**场景还原：**
- 开发者发布 Skill 后，再次编辑时状态仍显示"已发布"，用户无法区分已发布版本和编辑中版本
- 多次发布后无法追溯历史版本，出现问题无法回滚

**功能要求：**
1. 发布后编辑时状态变为"编辑中"
2. 再次发布时版本号递增（如 v1.0 → v1.1）
3. 支持查看版本历史
4. 支持一键恢复历史版本

**验证标准：**
- 已发布 Skill 编辑后状态是否正确变更
- 重新发布后版本号是否正确递增
- 能否查看历史版本
- 能否回滚到指定历史版本


### 1.3 为什么现在必须做

| 驱动因素 | 说明 |
|---------|------|
| 客户已签约 | 振兴集团等客户即将进入正式开发阶段，需要生产级可靠性 |
| AI 生成代码 | Build 的核心是 AI 驱动开发，AI 每次生成的结果不确定，更需要版本管理来兜底 |
| 多制品类型 | 6 种以上制品类型即将并行开发，统一设计成本最低 |
| 差异化声明 | 产品规划 v9 中"版本管理+灰度发布"已列为差异化优势，需兑现 |
| 企业治理 | 目标客户（央企/金融）要求审计追溯能力 |

### 1.3 范围

本方案覆盖 Build 中以下制品类型的版本管理：

| 制品类型 | 文件形态 | 典型大小 |
|---------|---------|---------|
| 智能体（Agent） | agent.md + assistant.json + 配置 | 小（KB级） |
| 技能（Skill） | SKILL.md + manifest.yaml + response.json | 小（KB级） |
| 通用应用 | 前端/后端代码工程 | 中大（MB级） |
| 苍穹应用 | 元数据 + 插件代码 | 中（KB-MB） |
| MCP APPS | React/Vue 代码 + info.json | 中（KB-MB） |
| MCP Server | 后端服务代码 | 中大（MB级） |

## 二、设计约束与前提

以下 7 个 Build 平台特征是本方案的核心设计约束，所有方案选型都围绕它们展开：

| # | 平台特征 | 对版本管理方案的影响 |
|---|---------|-------------------|
| 1 | **用户分层极大** — 从零代码业务专家到全栈开发者，跨度非常大 | 不能只提供 Git 式专业界面，必须按用户类型分层暴露能力（简洁/专业/管理员模式） |
| 2 | **制品类型多** — 智能体、Skill、苍穹应用、通用应用、MCP APPS、MCP Server（至少 6 类） | 版本管理模型必须统一抽象，不能每种制品单独设计一套，否则维护成本不可控 |
| 3 | **制品有依赖关系** — 智能体引用 Skill，Skill 引用 MCP Tool/APPS，APPS 关联 MCP 连接器 | 发布时必须记录依赖快照；回滚时必须能整体恢复到确定状态 |
| 4 | **双轨并行** — 苍穹生态轨（低代码/元数据）+ 通用技术栈轨（全栈代码） | 版本管理需同时适配"元数据配置"和"代码工程"两种完全不同的制品形态 |
| 5 | **AI 驱动开发** — 对话式生成，用户可能完全不碰代码 | AI 每次生成结果不确定，更需要自动版本保存来兜底；变更追溯需区分"人改的"和"AI 生成的" |
| 6 | **有发布上线流程** — Build → Console（审核上架）→ Work（运行时） | 版本管理需覆盖"开发态"和"发布态"两层，发布态需要不可变快照保证线上稳定 |
| 7 | **企业级治理** — 需要审计、权限、灰度、回滚 | 所有版本操作必须留痕可追溯，支持权限控制（谁能发布/谁能回滚），满足合规要求 |

> **这些约束决定了：** 我们不能简单照搬任何一家竞品的方案。Dify/Coze 太简单（无法覆盖多制品+企业治理），Mendix/OutSystems 太重（不适合 AI 驱动+对话式开发）。需要走"底层 Git + 上层分层抽象 + 快照式依赖管理"的组合路线。

## 三、业界方案调研

### 3.1 产品规划竞品的版本管理做法

产品规划=中对标的三个竞品（WorkBuddy、Claude Code、Codex）以及 OpenAI 最新的 AgentKit：

| 竞品 | 版本管理做法 | 优点 | 缺点 | 对灵基的启示 |
|------|------------|------|------|------------|
| **WorkBuddy（腾讯）** | 本地沙箱运行，无明确的制品版本管理体系；CodeBuddy IDE 侧依赖 Git；Agent 部署通过 Cloud Studio 一键部署，无版本回滚能力 | 部署简单，一键上云 | 无版本历史、无回滚、无审计；不适合企业级场景 | WorkBuddy 偏轻量工具，版本管理是我们的差异化超越点 |
| **Claude Code** | 底层完全基于 Git：每次 AI 修改自动 commit，会话历史持久化到本地（~/.claude/projects）。社区补充了 Checkpoints 工具（项目快照+可视化 diff）和 Cloud Session Sync（会话 Git 同步） | Git-native，天然支持分支/回滚/diff；AI 修改全量可追溯 | 面向开发者，无"发布版本"概念，无企业级环境管理；需要用户懂 Git | 验证了"AI 开发场景下 Git 自动 commit"的可行性；我们需要在此基础上加"发布版本"层 |
| **Codex（OpenAI）** | 深度集成 GitHub/GitLab：每个任务自动创建分支、生成 PR、支持 code review 和自动合并。GitHub Action 支持 CI/CD 流水线中运行 Codex。有审批流但仅代码维度 | PR 工作流成熟；CI/CD 集成完整；自动化程度高 | 仅覆盖代码类制品，不涉及 Agent/Skill 的版本管理；完全依赖外部 Git，无内置版本服务 | 验证了"AI 自动创建分支+PR"模式对开发者有效；但灵基还要覆盖非代码制品 |
| **AgentKit / Agent Builder（OpenAI，2026.7 新发布）** | 可视化画布构建 Agent 工作流，支持 preview runs + inline eval + **full versioning**；发布"versioned snapshots"不可变快照 | 快照式版本管理+预览+评测一体；面向非开发者友好 | 仅覆盖 Agent 工作流，不含代码/应用/Skill；版本管理细节未公开文档 | 最接近灵基需要的模式：快照 + 预览 + 评测 + 发布，验证了这套组合的行业方向 |

**关键发现：**

> 1. **没有任何一家竞品做到了"多制品类型统一版本管理"** — Claude Code/Codex 只管代码，AgentKit 只管 Agent 工作流，WorkBuddy 基本没做
> 2. **"AI 自动 commit"已成行业共识** — Claude Code 和 Codex 都在 AI 修改后自动创建 Git 记录
> 3. **"不可变快照发布"是 Agent 平台的正确方向** — AgentKit、Claude Managed Agents、ElevenLabs 都采用了这种模式
> 4. **灵基有机会做差异化** — 统一 6 类制品 + 分层用户体验 + 企业治理 = 竞品覆盖不了的空间

### 3.3 低代码/AI 平台的版本管理做法（补充参考）

| 平台 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **Mendix** | 内置 Git（Team Server），每个项目自动创建 Git 仓库，支持分支和合并 | 专业级能力完整；多人协作好 | 对非技术用户门槛高 |
| **OutSystems** | 平台托管版本，LifeTime 管理环境流转（Dev→QA→Prod），自动依赖分析 | 对业务用户友好；环境管理强 | 不暴露底层版本控制；灵活度低 |
| **Salesforce** | DevOps Center（Git-based）+ Change Sets（平台托管），双轨并行 | 兼顾两类用户；Agent ALM 新增 5 阶段生命周期 | 体系复杂，学习成本高 |
| **Dify** | 版本控制面板：track changes / publish / restore，每次发布自动创建不可变快照 | 简单直观；快照式好理解 | 无分支；无多人并行 |
| **Coze/扣子** | 发布版本号管理，支持回滚到历史版本 | 极简；用户无感 | 仅支持发布态回滚，开发过程无版本 |
| **Claude Managed Agents** | 不可变版本（immutable version），每次更新产生新版本 ID，通过 config 指向活跃版本 | 简洁安全；回滚即切换指针 | 偏 API 化，无可视化 |
| **ElevenLabs Agents** | 分支+流量百分比部署（Agent Versioning + Traffic % Deployment） | 支持 A/B 测试和渐进发布 | 仅针对 Agent 单一制品 |

### 3.4 AI Agent 版本管理的特殊性

AI 智能体与传统软件不同，需要额外考虑：

| 特殊点 | 说明 | 影响 |
|--------|------|------|
| 非确定性 | 同一版本的智能体，行为也可能不同（模型温度、上下文） | 版本 != 行为一致性，需配合评测 |
| 复合系统 | Agent = Prompt + Model + Tools + Knowledge + Memory | 版本需要是"全量快照"而非单文件 |
| 隐式变更 | 底层模型升级、知识库更新会导致行为变化 | 需记录"环境指纹"（模型版本、知识库版本） |
| 行为漂移 | 长期运行后记忆积累导致行为偏移 | 需要能"重置到某版本的初始状态" |

### 3.5 行业共识总结

1. **发布态必须是不可变快照（Immutable Snapshot）** — 这是所有平台的共识
2. **开发过程需要变更追溯** — 至少要有"谁在什么时候改了什么"
3. **回滚是核心能力** — 线上出问题时能秒回上一版
4. **对非技术用户屏蔽复杂性** — Git 概念太重，需要包装
5. **制品粒度版本 + 整体发布包** — 两层都需要

## 四、方案设计

### 4.1 核心设计原则

| 原则 | 说明 |
|------|------|
| **两层版本** | 制品级版本（开发时）+ 发布包版本（上线时），分层管理 |
| **底层 Git，上层包装** | 存储用 Git 保证可靠性和扩展性，用户界面做简化抽象 |
| **快照即版本** | 每个"版本"是制品全量状态的不可变快照，不是 diff |
| **按用户分层暴露** | 业务用户看"版本列表+回滚"；技术用户可选深入到分支/diff |
| **统一模型** | 6 种制品用同一套版本管理机制，体验一致 |

### 4.3 制品生命周期状态机

基于振兴客户需求明确的状态流转规则：

```
┌─────────┐      保存       ┌─────────┐     发布(v1.0)    ┌─────────┐
│  新建   │ ──────────────▶ │ 开发中  │ ──────────────── ▶│ 已发布  │
└─────────┘                  └─────────┘                    └────┬────┘
                                  ▲                              │
                                  │          再次编辑            │
                                  │◀─────────────────────────────┘
                                  │                         状态变为"编辑中"
                                  ▼
                             ┌─────────┐     发布(v1.1)    ┌─────────┐
                             │ 编辑中  │ ──────────────── ▶│ 已发布  │
                             │(有未发布 │                    │ (新版本)│
                             │ 的修改) │                    └─────────┘
                             └─────────┘
```

**状态定义：**

| 状态 | 含义 | 用户可见标识 |
|------|------|------------|
| 新建 | 刚创建，从未保存 | — |
| 开发中 | 有保存但从未发布 | "草稿" |
| 已发布 | 当前线上运行的版本 = 最后保存的版本 | "已发布 v1.2.0" |
| 编辑中 | 已发布后又有了新的修改，线上版本 ≠ 当前编辑版本 | "已发布 v1.2.0 · 有未发布的修改" |
| 已回滚 | 曾经发布但被回滚替代的旧版本 | "v1.2.0 (已回滚)" |

**关键规则：**
1. "已发布"状态的制品一旦被编辑，状态**立即**变为"编辑中"
2. "编辑中"状态再次发布后，版本号递增，状态回到"已发布"
3. 线上始终运行最新的"已发布"版本，"编辑中"的修改不影响线上
4. 回滚操作将线上切换到历史某个"已发布"版本，当前版本标记为"已回滚"

### 4.5 两层版本模型

#### 第一层：开发版本（Draft Version）

**触发时机：** 用户每次保存 / AI 每次完成一轮生成

**做什么：**
- 自动创建一个 commit（用户无感）
- 记录：谁（用户/AI）、什么时间、改了什么文件
- 自动生成变更摘要（AI 生成一句话描述本次变更）

**用户可见：**
- 开发版本时间线（类似 Google Docs 的版本历史）
- 每个版本可预览、可回退
- 可 diff 两个版本

**数据模型：**

```json
{
  "versionId": "dv-20260803-001",
  "artifactType": "skill",
  "artifactId": "create-ticket-skill",
  "projectId": "helpdesk-project",
  "author": {
    "type": "user | ai",
    "userId": "user-123",
    "name": "张三"
  },
  "timestamp": "2026-08-03T10:30:00Z",
  "summary": "修改了工单创建的必填字段校验逻辑",
  "snapshot": {
    "files": [
      { "path": "SKILL.md", "hash": "abc123" },
      { "path": "manifest.yaml", "hash": "def456" }
    ]
  },
  "parentVersionId": "dv-20260803-000",
  "gitCommitSha": "a1b2c3d4..."
}
```

#### 第二层：发布版本（Release Version）

**触发时机：** 用户点击"发布"

**做什么：**
- 创建不可变快照（Immutable Snapshot）
- 生成语义化版本号（v1.0.0 / v1.1.0 / v2.0.0）
- 记录发布时的完整环境指纹（模型版本、知识库版本、依赖的其他制品版本）
- 推送到 Console 或 Work 运行时

**用户可见：**
- 发布版本列表（v1.0、v1.1、v2.0…）
- 每个版本的发布说明（Release Notes）
- 一键回滚到任意历史发布版本
- 当前线上运行的是哪个版本

**数据模型：**

```json
{
  "releaseId": "rv-1.2.0",
  "version": "1.2.0",
  "artifactType": "agent",
  "artifactId": "helpdesk-assistant",
  "projectId": "helpdesk-project",
  "releasedBy": "user-123",
  "releasedAt": "2026-08-03T14:00:00Z",
  "releaseNotes": "新增 SLA 超时告警能力，修复多轮对话丢失上下文问题",
  "snapshot": {
    "files": [...],
    "gitTag": "release/helpdesk-assistant/v1.2.0"
  },
  "environment": {
    "modelVersion": "claude-5-20260701",
    "knowledgeBaseVersion": "kb-v3",
    "dependencies": [
      { "type": "skill", "id": "create-ticket-skill", "version": "1.1.0" },
      { "type": "skill", "id": "knowledge-qa-skill", "version": "2.0.0" },
      { "type": "mcpapp", "id": "ticket-confirm-card", "version": "1.0.0" }
    ]
  },
  "status": "active | superseded | rolled-back",
  "immutable": true
}
```

### 4.6 依赖管理策略（渐进式）

**核心思路：第一阶段用"发布时快照"隐式管理依赖，不做强制版本锁定。**

| 阶段 | 策略 | 用户体验 |
|------|------|---------|
| 第一阶段 | **快照式** — 发布时自动记录引用的各依赖的当前版本，回滚时整体回滚 | 用户无感，系统自动处理 |
| 第二阶段 | **提示式 + lock 文件** — 每个 Agent 维护一个 `dependencies.lock`（类似 npm 的 package-lock.json），记录所依赖的 Skill/MCP Tool 的精确版本号。依赖有更新时提示"Skill X 有新版本 v1.2.0，是否更新引用？" | 用户看到更新提示，自主决策；lock 文件随制品版本一起管理 |
| 第三阶段 | **锁定式** — 支持手动锁定依赖版本，依赖冲突自动检测，支持版本范围声明（如 `^1.0.0` 表示兼容 1.x） | 类似 npm lock，适合复杂项目 |

**第二阶段 `dependencies.lock` 结构示例：**

```json
{
```

## 五、各制品类型的差异化处理

虽然版本管理模型统一，但各制品类型在具体实现上有细微差异：

| 制品类型 | 版本粒度 | 发布目标 | 特殊考虑 |
|---------|---------|---------|---------|
| 智能体 | 整个智能体（含 Skill 引用快照） | Work 运行时 | 需记录模型版本+知识库版本作为环境指纹 |
| Skill | 单个 Skill | 智能体引用/Skill 市场 | 被多个智能体引用时，版本升级需通知引用方 |
| 通用应用 | 整个应用工程 | 部署环境（容器/CDN） | 需要构建步骤（build），产物较大 |
| 苍穹应用 | 元数据 + 插件 | 苍穹云部署 | 需兼容苍穹自身的版本管理机制 |
| MCP APPS | 整个 APPS 项目 | Console 组件仓库 | 需 vite build → zip → 上传，版本由 Console 管理 |
| MCP Server | 服务端代码 | 部署环境（容器/K8s） | **双重版本管理**：代码版本（Git 管理源码）+ 服务版本（CI/CD 构建镜像 → 部署运行）。代码版本对应 Git 标签，服务版本对应运行中的 Docker 镜像标签。回滚需同时考虑代码回退和服务重新部署。版本号需遵循 SemVer 规范（主版本=不兼容 API 变更，次版本=向下兼容功能新增，修订号=Bug修复），因为 Agent 作为客户端依赖 MCP Server 的 API 兼容性 |

## 六、技术选型建议

### 6.1 存储层：为什么选 Git

| 考虑 | Git | 自建版本存储 | 数据库快照 |
|------|-----|-------------|-----------|
| 成熟度 | ★★★★★ | ★★ | ★★★ |
| diff 能力 | ★★★★★ | 需自建 | 无 |
| 分支合并 | ★★★★★ | 需自建 | 无 |
| 生态工具 | ★★★★★ | 无 | 有限 |
| 大文件 | ★★★ (Git LFS) | 可定制 | ★★★★ |
| 对用户透明 | 需包装 | 完全可控 | 完全可控 |
| 开发成本 | 低（现成库） | 高（从零开始） | 中 |

**结论：用 Git 作为底层存储，上层做 UI 抽象。** 理由：
- Git 是行业标准，Mendix、Salesforce 都走了这条路
- diff、分支、合并等能力不需要重新发明
- 未来可以对接外部 Git 服务（GitHub/GitLab），满足企业 DevOps 需求
- 对非技术用户完全屏蔽 Git 概念，只暴露"版本列表"和"回滚"

### 6.2 用户界面抽象程度

| 用户类型 | 看到什么 | 不看到什么 |
|---------|---------|-----------|
| 业务专家/全员开发 | 版本列表、回滚按钮、变更时间线 | Git、commit、branch、merge |
| 开发者（可选开启） | 上述 + diff 视图、分支管理 | raw git 命令行 |
| IT 管理员 | 上述 + 审计日志、权限控制、合规报告 | — |

## 七、分阶段实施计划

### Phase 1：基础版本能力

#### ⚡ Phase 1a：最小可行交付（目标：解决振兴刚需）

**不用 Git、不用重构底层，用最轻量的方式先交付：**

| # | 功能 | 实现方式 | 工期预估 |
|---|------|---------|---------|
| 1 | 发布版本号递增 | 发布时写一条版本记录到数据库（版本号+时间+操作人+制品快照 URL） | 2-3 天 |
| 2 | 制品状态变更 | 制品增加 status 字段：draft / published / editing。编辑已发布制品时自动切为 editing | 1-2 天 |
| 3 | 版本历史列表 | 从数据库查版本记录，展示列表（版本号+时间+操作人） | 2-3 天 |
| 4 | 一键回滚 | 将历史版本的快照还原为当前版本，推送到运行时 | 2-3 天 |

**技术实现（极简版）：**
- 每次"发布"时，将当前制品的全部文件打包存到对象存储（OSS/S3），数据库记录一条版本元数据
- 回滚 = 取出历史快照覆盖当前 + 通知运行时重新加载
- 不改底层存储架构，不引入 Git，不做 diff

**覆盖范围：** 先只做 Skill + Agent（振兴当前需要的）

**验收标准：** 就是振兴提出的那 4 条

> 这是"能跑"的底线。振兴客户拿到后可以正常工作，我们也有时间做后面的事。

#### Phase 1b：补齐基础能力

| # | 功能 | 描述 | 价值 |
|---|------|------|------|
| 5 | 自动保存历史 | 每次保存自动存快照，用户可查看修改时间线 | 误操作可回退（不只是发布态） |
| 6 | 变更摘要 | AI 自动生成每次变更的一句话描述 | 可追溯 |
| 7 | 覆盖更多制品 | 扩展到通用应用、MCP APPS 等 | 统一体验 |
| 8 | 底层切 Git（可选） | 评估是否需要将存储改为 Git，为后续 diff/分支做准备 | 技术债预防 |

**决策点：Phase 1b 做完后评估是否需要切 Git。** 如果业务上不需要 diff/分支/多人协作，数据库快照方案可以长期用下去。

### Phase 2：协作与追溯

| # | 功能 | 描述 |
|---|------|------|
| 7 | 变更 diff | 可视化对比两个版本的差异（逐行/结构化） |
| 8 | 审计日志 | 完整记录谁、什么时候、做了什么操作 |
| 9 | 发布说明 | 发布时填写/AI生成 Release Notes |
| 10 | 依赖快照 | 发布时自动记录所依赖的其他制品版本 |
| 11 | 版本对比评测 | Skill/智能体两个版本的效果对比（集成 Eval） |

### Phase 3：高级能力

| # | 功能 | 描述 |
|---|------|------|
| 12 | 分支开发 | 支持创建分支并行开发，合并回主线 |
| 13 | 环境管理 | 开发→测试→生产 多环境版本流转 |
| 14 | 灰度发布 | 按百分比/租户/组织灰度切换新版本（待讨论具体方案） |
| 15 | 外部 Git 对接 | 支持对接 GitHub/GitLab，双向同步 |
| 16 | 依赖更新提示 | 引用的 Skill/APPS 有新版时通知更新 |

## 十、风险评估

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 底层改 Git 对已有项目有破坏性 | 中 | 高 | 需设计无损迁移方案，灰度切换 |
| Git 对大型应用项目性能不佳 | 低 | 中 | 大文件用 Git LFS，代码类无问题 |
| 非技术用户不理解"版本"概念 | 中 | 中 | UI 极简化，默认隐藏所有 Git 概念 |
| 各制品类型的版本管理需求差异大 | 中 | 中 | 统一底层模型，表层按类型微调 |
| 版本存储成本增长 | 低 | 低 | Git 增量存储天然高效；加过期策略 |
