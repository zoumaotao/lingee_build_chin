Build 统一版本管理能力方案设计

灵基 Build 全制品类型的版本管理能力顶层设计
面向：Build产品团队、Harness团队、Console团队 | 日期：2026-08-03 | 状态：方案初稿，待评审

一、问题定义

1.1 现状

灵基 Build 当前对所有制品类型的存储机制：每次保存直接覆盖上一次，无任何历史记录。

  • 开发者误操作无法回退
  • 无法对比"上次能跑的版本"和"这次改坏的版本"
  • 发布到 Work 后发现问题无法回滚
  • AI 自动生成代码后，人无法审查"改了什么"
  • 多人协作会互相覆盖
  • 无法满足企业级审计要求（谁、什么时候、改了什么）

1.2 客户真实需求（振兴集团提出）

原始需求：Skill 需要支持研发版本化。发布出去的 Skill/Agent 在重新编辑重新发布后，状态需要调整，体现已被重新编辑。再次发布后，版本编号需要跟上次有差异。

功能要求：

  1. 发布后编辑时状态变为"编辑中"
  2. 再次发布时版本号递增（如 v1.0 → v1.1）
  3. 支持查看版本历史
  4. 支持一键恢复历史版本

1.3 范围

制品类型文件形态典型大小
智能体（Agent）agent.md + assistant.json + 配置小（KB级）
技能（Skill）SKILL.md + manifest.yaml + response.json小（KB级）
通用应用前端/后端代码工程中大（MB级）
苍穹应用元数据 + 插件代码中（KB-MB）
MCP APPSReact/Vue 代码 + info.json中（KB-MB）
MCP Server后端服务代码中大（MB级）

二、设计约束与前提

以下 7 个 Build 平台特征是本方案的核心设计约束，所有方案选型都围绕它们展开：

#平台特征对版本管理方案的影响
1用户分层极大 — 从零代码业务专家到全栈开发者必须按用户类型分层暴露能力（简洁/专业/管理员模式）
2制品类型多 — 至少 6 类制品版本管理模型必须统一抽象，不能每种制品单独设计
3制品有依赖关系 — Agent→Skill→MCP发布时必须记录依赖快照；回滚时整体恢复
4双轨并行 — 苍穹生态轨 + 通用技术栈轨需同时适配"元数据配置"和"代码工程"两种形态
5AI 驱动开发 — 对话式生成，结果不确定更需要自动版本保存兜底；需区分"人改的"和"AI 生成的"
6有发布上线流程 — Build → Console → Work需覆盖"开发态"和"发布态"两层版本
7企业级治理 — 审计、权限、灰度、回滚所有操作留痕可追溯，支持权限控制
这些约束决定了：不能简单照搬任何一家竞品的方案。Dify/Coze 太简单（无法覆盖多制品+企业治理），Mendix/OutSystems 太重（不适合 AI 驱动+对话式开发）。建议需要走"底层 Git + 上层分层抽象 + 快照式依赖管理"的组合路线。

三、业界方案调研

3.1 产品规划竞品分析

WorkBuddy（腾讯）

本地沙箱运行，无明确版本管理体系；Agent 部署通过 Cloud Studio 一键部署，无版本回滚能力
✓ 部署简单，一键上云
✗ 无版本历史、无回滚、无审计

Claude Code

底层完全基于 Git：每次 AI 修改自动 commit，会话历史持久化。社区补充 Checkpoints 工具
✓ Git-native，天然支持分支/回滚/diff
✗ 无"发布版本"概念，需懂 Git

Codex（OpenAI）

深度集成 GitHub/GitLab：每个任务自动创建分支、生成 PR、支持 code review 和自动合并
✓ PR 工作流成熟；CI/CD 集成完整
✗ 仅覆盖代码类制品，完全依赖外部 Git

AgentKit（OpenAI 2026.7）

可视化画布构建 Agent 工作流，支持 preview runs + inline eval + full versioning；发布不可变快照
✓ 快照式版本管理+预览+评测一体
✗ 仅覆盖 Agent 工作流，不含代码/Skill

🔍 关键发现

  1. 没有竞品已经做到"多制品类型统一版本管理" — Claude Code/Codex 只管代码，AgentKit 只管 Agent 工作流
  2. "AI 自动 commit"已成行业共识 — Claude Code 和 Codex 都在 AI 修改后自动创建 Git 记录
  3. "不可变快照发布"是 Agent 平台的正确方向 — AgentKit、Claude Managed Agents、ElevenLabs 都采用
  4. 灵基有机会做差异化 — 统一 6 类制品 + 分层用户体验 + 企业治理 = 竞品覆盖不了的空间

3.2 低代码/AI 平台参考

平台做法优点缺点
Mendix内置 Git（Team Server），每个项目自动创建 Git 仓库专业级能力完整；多人协作好对非技术用户门槛高
OutSystemsLifeTime 管理环境流转（Dev→QA→Prod）对业务用户友好；环境管理强不暴露底层版本控制
SalesforceDevOps Center（Git-based）+ Change Sets 双轨兼顾两类用户；Agent ALM 5 阶段生命周期体系复杂，学习成本高
Difytrack changes / publish / restore，快照不可变简单直观；快照式好理解无分支；无多人并行
Coze/扣子发布版本号管理，支持回滚历史版本极简；用户无感仅发布态回滚，开发过程无版本
Claude Managed Agents不可变版本，每次更新产生新版本 ID简洁安全；回滚即切换指针偏 API 化，无可视化
ElevenLabs分支+流量百分比部署支持 A/B 测试和渐进发布仅针对 Agent 单一制品

3.3 AI Agent 版本管理特殊性

特殊点说明影响
非确定性同一版本的智能体，行为也可能不同（模型温度、上下文）版本 ≠ 行为一致性，需配合评测
复合系统Agent = Prompt + Model + Tools + Knowledge + Memory版本需要是"全量快照"而非单文件
隐式变更底层模型升级、知识库更新导致行为变化需记录"环境指纹"（模型版本、知识库版本）
行为漂移长期运行后记忆积累导致行为偏移需要能"重置到某版本的初始状态"

3.4 行业共识

  1. 发布态必须是不可变快照（Immutable Snapshot） — 这是所有平台的共识
  2. 开发过程需要变更追溯 — 至少要有"谁在什么时候改了什么"
  3. 回滚是核心能力 — 线上出问题时能秒回上一版
  4. 对非技术用户屏蔽复杂性 — Git 概念太重，需要包装
  5. 制品粒度版本 + 整体发布包 — 两层都需要

四、方案设计

4.1 核心设计原则

原则说明
两层版本制品级版本（开发时）+ 发布包版本（上线时），分层管理
底层 Git，上层包装存储用 Git 保证可靠性和扩展性，用户界面做简化抽象
快照即版本每个"版本"是制品全量状态的不可变快照，不是 diff
按用户分层暴露业务用户看"版本列表+回滚"；技术用户可选深入到分支/diff
统一模型6 种制品用同一套版本管理机制，体验一致

4.2 整体架构

4.3 制品生命周期状态机

状态含义用户可见标识
新建刚创建，从未保存—
开发中有保存但从未发布"草稿"
已发布当前线上运行的版本 = 最后保存的版本"已发布 v1.2.0"
编辑中已发布后又有了新修改，线上 ≠ 当前编辑"已发布 v1.2.0 · 有未发布的修改"
已回滚曾经发布但被回滚替代的旧版本"v1.2.0 (已回滚)"

4.4 两层版本模型

第一层：开发版本（Draft Version）

触发时机：用户每次保存 / AI 每次完成一轮生成

  • 自动创建一个 commit（用户无感）
  • 记录：谁（用户/AI）、什么时间、改了什么文件
  • 自动生成变更摘要（AI 生成一句话描述本次变更）

第二层：发布版本（Release Version）

触发时机：用户点击"发布"

  • 创建不可变快照（Immutable Snapshot）
  • 生成语义化版本号（v1.0.0 / v1.1.0 / v2.0.0）
  • 记录发布时的完整环境指纹（模型版本、知识库版本、依赖版本）
  • 推送到 Console 或 Work 运行时

4.5 依赖管理策略（渐进式）

阶段策略用户体验
第一阶段 快照式 — 发布时自动记录引用的各依赖当前版本，回滚时整体回滚 用户无感，系统自动处理
第二阶段 提示式 — 依赖更新时提示"Skill X 有新版本，是否更新引用？" 用户看到更新提示，自主决策
第三阶段 锁定式 — 支持手动锁定依赖版本，依赖冲突自动检测 类似 npm lock，适合复杂项目

六、技术选型

6.1 存储层方案对比

考虑Git自建版本存储数据库快照
成熟度★★★★★★★★★★
diff 能力★★★★★需自建无
分支合并★★★★★需自建无
生态工具★★★★★无有限
大文件★★★ (Git LFS)可定制★★★★
对用户透明需包装完全可控完全可控
开发成本低（现成库）高（从零开始）中
结论：用 Git 作为底层存储，上层做 UI 抽象。

理由：Git 是行业标准（Mendix、Salesforce 都走了这条路）；diff、分支、合并等能力不需要重新发明；未来可对接外部 Git 服务（GitHub/GitLab），满足企业 DevOps 需求；对非技术用户完全屏蔽 Git 概念，只暴露"版本列表"和"回滚"。

6.2 用户界面抽象程度

用户类型看到什么不看到什么
业务专家/全员开发版本列表、回滚按钮、变更时间线Git、commit、branch、merge
开发者（可选开启）上述 + diff 视图、分支管理raw git 命令行
IT 管理员上述 + 审计日志、权限控制、合规报告—

七、分阶段实施计划

Phase 1a：最小可行交付

⚡ 目标：解决振兴刚需

不用 Git、不用重构底层，用最轻量的方式先交付：

#功能实现方式工期
1发布版本号递增发布时写一条版本记录到数据库（版本号+时间+操作人+快照 URL）2-3 天
2制品状态变更制品增加 status 字段：draft/published/editing。编辑已发布制品时自动切为 editing1-2 天
3版本历史列表从数据库查版本记录，展示列表（版本号+时间+操作人）2-3 天
4一键回滚将历史版本的快照还原为当前版本，推送到运行时2-3 天
技术实现（极简版）：
  • 每次"发布"时，将制品全部文件打包存到对象存储（OSS/S3），数据库记录版本元数据
  • 回滚 = 取出历史快照覆盖当前 + 通知运行时重新加载
  • 不改底层存储架构，不引入 Git，不做 diff

覆盖范围：先只做 Skill + Agent（振兴当前需要的）

Phase 1b：补齐基础能力

#功能描述价值
5自动保存历史每次保存自动存快照，用户可查看修改时间线误操作可回退（不只是发布态）
6变更摘要AI 自动生成每次变更的一句话描述可追溯
7覆盖更多制品扩展到通用应用、MCP APPS 等统一体验
8底层切 Git（可选）评估是否需要将存储改为 Git技术债预防
决策点：Phase 1b 做完后评估是否需要切 Git。如果业务上不需要 diff/分支/多人协作，数据库快照方案可以长期用下去。

Phase 2：协作与追溯

#功能描述
7变更 diff可视化对比两个版本的差异（逐行/结构化）
8审计日志完整记录谁、什么时候、做了什么操作
9发布说明发布时填写/AI 生成 Release Notes
10依赖快照发布时自动记录所依赖的其他制品版本
11版本对比评测Skill/智能体两个版本的效果对比（集成 Eval）

Phase 3：高级能力

#功能描述
12分支开发支持创建分支并行开发，合并回主线
13环境管理开发→测试→生产 多环境版本流转
14灰度发布按百分比/租户/组织灰度切换新版本
15外部 Git 对接支持对接 GitHub/GitLab，双向同步
16依赖更新提示引用的 Skill/APPS 有新版时通知更新

十、风险评估

风险概率影响应对措施
底层改 Git 对已有项目有破坏性 中 高 需设计无损迁移方案，灰度切换
Git 对大型应用项目性能不佳 低 中 大文件用 Git LFS，代码类无问题
非技术用户不理解"版本"概念 中 中 UI 极简化，默认隐藏所有 Git 概念
各制品类型的版本管理需求差异大 中 中 统一底层模型，表层按类型微调
版本存储成本增长 低 低 Git 增量存储天然高效；加过期策略
